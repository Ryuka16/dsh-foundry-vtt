## 二 · 排查过程（含一次被我推翻的错误假设）

### 2.1 我最初的错误推断

我测到卡上有三份相关物品：

| 物品 | id | max | advanceOrigin |
|---|---|---|---|
| 地狱遗赠 (提夫林) | `UXmoM7Nuut2m8LAE` | 2 | `VjBTdCQH9aVGuaOB.1TyE6rcEq01VWRZc` |
| 炼狱叱喝 Hellish Rebuke | `wcQd1fdRsWrzYsOB` | 1 | `VjBTdCQH9aVGuaOB.d8rqpB59h8lfbnva` |
| 炼狱叱喝 Hellish Rebuke | `vbpHJFoAghGGAWs6` | 空 | **null** |

第三份 `advancementOrigin` 为 null、创建时间比第二份晚 69 秒 ⇒ 我推断「用户手动从包里拖了一份副本」。

**用户否定了这个推断**：「但是我没脱过副本啊？」

**⇒ 按 AGENTS.md 指标一（用户的描述是事实，我的推断是假设，冲突时改假设），重新排查。**

### 2.2 真根因 —— 是 dnd5e 自己建的

第三份物品的 flags 里写着：

```json
flags.dnd5e = {
  "migratedProperties": ["vocal", "somatic"],
  "riders": { "activity": [], "effect": [] },
  "cachedFor": ".Item.UXmoM7Nuut2m8LAE.Activity.SdhCJiUZZeOQNfg8",
  "last": { "dnd5eactivity000": { "damageType": { "0": "fire" } } }
}
```

`cachedFor` 指向 **地狱遗赠 feat 的第 2 条 cast 活动（炼狱叱喝）**。

**⇒ 结论：用户点「地狱遗赠（提夫林）:炼狱叱喝」按钮施放时，dnd5e 自动在卡上缓存了一份法术副本。** 这是 dnd5e 的 `cast` 活动机制，不是用户拖的。

### 2.3 dnd5e 源码证据（`systems/dnd5e/dnd5e.mjs`，3,007,943 字符）

```js
// ① 查找缓存法术（严格按 cachedFor 标记匹配）
get cachedSpell() {
  return this.actor?.sourcedItems.get(this.spell.uuid)
    ?.find(i => i.getFlag("dnd5e", "cachedFor") === this.relativeUUID);
}

// ② 缓存法术是否列进法术书
get displayInSpellbook() {
  return this.canUse && (this.item.system.magicAvailable !== false) && this.spell.spellbook;
}

// ③ 法术书准备时对缓存法术的处理
if ( spell.getFlag("dnd5e", "cachedFor") ) {
  method = "item";
  if ( !spell.system.linkedActivity?.displayInSpellbook ) return;   // 不达条件就不列
  registerSection(method);
}

// ④ 缓存法术反查它所属的活动
get linkedActivity() {
  const relative = this.parent.actor;
  const uuid = this.parent.getFlag("dnd5e", "cachedFor");
  if ( !relative || !uuid ) return null;
  const data = foundry.utils.parseUuid(uuid, { relative });
  const [itemId, , activityId] = (data?.embedded ?? []).slice(-3);
  return relative.items.get(itemId)?.system.activities?.get(activityId) ?? null;
}
```

**⇒ `displayInSpellbook` 的三要素：`canUse` ∧ `magicAvailable !== false` ∧ `spell.spellbook`。**
**⇒ 本包 120 条 cast 活动的 `spell.spellbook` 全是 `true` ⇒ 缓存副本被列进法术书 ⇒ 被 midi 反应框列出。**
**⇒ 而缓存副本自己的 `uses.max` 是空 ⇒ 看起来「无限次」。**

## 三 · 实测验证（全部在本世界跑通）

| # | 实验 | 结果 |
|---|---|---|
| 1 | 删除缓存副本 → 重置 feat 次数 → 点火「地狱遗赠:炼狱叱喝」 | 副本**重新长出来**，feat 次数 0/2 → 1/2（正常扣） |
| 2 | 直接点火**缓存副本**，看 feat 次数 | feat 0/2 → 1/2 ⇒ **会通过 linkedActivity 回扣 feat 次数** |
| 3 | feat 次数先耗到 2/2，再点火缓存副本 | 超时 7 秒、`spent` 仍是 2/2、midi 报错桶无新增 ⇒ **次数确实被拦住** |
| 4 | 把三条 cast 活动 `spellbook` 改 false → 重查三份缓存副本 | 三份 `displayInSpellbook` 全部 = `false` |
| 5 | 改后点火 feat 按钮 | 已完成、次数 0/2 → 1/2、报错桶 4→4 ⇒ **按钮与次数机制完全不受影响** |

**⇒ 定性：这不是「能无限施放」，而是「反应框/法术表里一直显示一个没有次数的副本，点了才失败」。用户看到的现象成立。**

**⇒ 附带发现：卡上删不掉的缓存副本属于已知的「僵尸物品」现象（`actor.items.get(id)` 拿得到，但 `deleteEmbeddedDocuments` 报 `Item "xxx" does not exist!`）。本次未处理，改 `spellbook` 后它们不再显示，无害。**

## 五 · 备份与回滚

**备份形式**：全部 120 条活动改前值**统一为 `spellbook: true`**（改前逐条读回确认过，无一例外）。
**回滚方法**：把上述 56 件的 cast 活动 `spell.spellbook` 设回 `true` 即可，脚本与本次改动完全对称。

**为什么回滚成本极低**：只动了一个布尔值，没有触碰任何数值、活动结构、效果、消耗、活动键名。

## 六 · 未改动 / 未验证项

- **未改 `itempack`（250 件有 cast 活动的魔法物品）** —— 官方魔杖（`Wand of Magic Detection` / `Wand of Magic Missiles` / `Wand of Web`…）实测同为 `spellbook = true`，本包与官方一致，不属于本次问题。
- **未改 `class-abilityphb`(42) / `extra-ability`(19) / `feats-all`(10)** —— 其中是否有「反应法术 + cast 活动」的组合尚未逐件筛。**判别方法**：若该 cast 活动的法术施放时间是「1 反应」，就会在 midi 反应框被列出，问题形态与本次相同。
- **未处理卡上的僵尸缓存副本**（`vbpHJFoAghGGAWs6` / `qs1Eaw3wqWDmCwbo` / `mc3NdNxOtIGypWNV` / `xyT6bCckmqLBlFag` / `7CS7x1S7tFYEt6ca`）—— 改后不再显示，无害。
- **旧卡上已拖出的 feat 副本不会自动更新** —— 需要重新从包拖一次才带上新配置。用户 PL 卡（维兰）上那份「地狱遗赠 (提夫林)」仍带旧配置，**未动用户的卡**。

## 七 · 相关事实（本轮顺带确认）

- 官方 `dnd5e.races` 提夫林的标准写法（本包 `races-item` 提夫林与之逐字段一致，**没有错**）：
  ```
  ItemGrant@L3 | spell.method = "innate" | spell.uses = {max:"1", per:"lr", requireSlot:false} | 炼狱叱喝
  ItemGrant@L5 | 同上 | 黑暗术
  ItemGrant@L0 | spell.uses = {max:"", per:""} | 奇术（戏法，本来就该无限）
  ```
- 用户真车卡「维兰」（提夫林术士 L3）拿到的炼狱叱喝 = `max:1`、`advancementOrigin` 有值 ⇒ **正常流程不产生多余的无限副本**。
- 「L3+ 无 max」共 204 条，逐条查明后：**龙纹法术 48 条 + 领域/结社/誓言法术 156 条，全部正确**（规则书原文：龙纹法术「将加入你施法职业的法术列表中」⇒ 用法术位，本来就不该有次数）。**0 条真错。**
