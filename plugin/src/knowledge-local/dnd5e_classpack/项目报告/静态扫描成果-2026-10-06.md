**机制**：`getRules(Item)` 读 `system.source.rules` —— `''`/`'2014'` → legacy 表，其他 → modern 表。
这 9 件物品标 2014 ⇒ 查 legacy 表 ⇒ 而宏只在 modern 表 ⇒ `getMacro` 返回 null
⇒ **CPR 静默跳过**（Q7：无警告、不抛错、不回退）。

**对照实证**：

```

warriorOfTheGods(modern) = 有:Warrior of the Gods
```

**这 9 件确实是「被动特性」，本来就该没有活动**（神之勇者=复活不需材料、追猎如风=未命中再打一次、
大德鲁伊=无限野性变形……）⇒ 「无活动」不是缺陷，**但「只能靠 CPR + CPR 里查不到」就是缺陷**。

**修法方向（用户已定）**：保持 `rules='2014'`，自己补 legacy 版宏。

## 四 · ★★ 关键判据：先问「这件依不依赖 CPR」

**这是本次最重要的方法论收获，我连错三轮。**

```
✗ 错误判据：identifier 在 CPR 表里查不到 ⇒ 判为错误
   ⇒ 把 29 件实现自足的件全冤枉了

✓ 正确判据：
  1. 有活动 ∨ 有效果 ∨ 有嵌入宏 ∨ 有 macros 绑定  ⇒ 实现自足 ⇒ CPR 断链只是少了加成，不是错误
  2. 四条全无 ⇒ 唯一实现途径就是 CPR 内置宏（靠 identifier 查）
     ├─ identifier 查得到 ⇒ 正常
     └─ identifier 查不到 ⇒ 完全没实现 ⇒ 真错误
```

**实证：全库 4093 件、挂 CPR 497 件，其中「四条全无」（完全依赖 CPR）的只有 26 件，26 件里出问题 10 件。**

### 案例：16 件「卓越技巧」战技 —— 不是错误，是有意的独立实现（用户确认）

**背景**（用户原话）：「我们之前确定卓越技巧会把卓越骰次数匹配错误，次特意做的，这个没必要必须CPR吧」

**数据完全支持**：

```
① 活动完整，脱离 CPR 就能跑
   maneuversMenacingAttackSuperiorTechnique  → [save+dmg+fx1]
   maneuversDistractingStrikeSuperiorTechnique → [damage+dmg+fx1]
   maneuversRiposteSuperiorTechnique          → [utility+fx1]
   ……16 件全部有实打实的活动

② 消耗已和战斗大师解耦
   我们的 16 件：{"type":"itemUses","value":"1","target":"superiority-dice-…"}
   战斗大师原件：{"type":"itemUses","value":"1","target":"Compendium.dnd5e_…"}

③ 两颗骰的 uses 确实不同 —— 正是当初要解决的问题
   卓越技巧 superiorityDiceSuperiorTechnique：uses.max = "1"，recovery = [{period:"sr",type:"recoverAll"}]
   战斗大师 superiorityDice：uses.max = "floor((@classes.fighter.levels+1)/8)+4"（随等级 4~8+）
   ⇒ 若共用 CPR 宏 getItemByIdentifier(actor,"superiorityDice") 取到错的那颗 ⇒ 次数全错
```

**来源与指纹**（证明是我们 2026-10-05 建的）：

```
战技: 恐吓攻击（作者原版）  maneuversMenacingAttack                    2024-09-07
战技: 恐吓攻击（我们建的）  maneuversMenacingAttackSuperiorTechnique  2026-10-05  v99.0.0
⇒ 16 件后缀件 createdTime 全部 = 2026-10-05，version 全部 = v99.0.0（我们统一写的哨兵值）
```

**遗留小事**：这 16 件还挂着 `flags["chris-premades"].info.identifier`（那个查不到的名字）。
运行时无害（无 macros 绑定 = CPR 根本不去查它），只在 CPR Medkit 界面显示成「已认领但应用不了」。清不清待定。

## 五 · ★ 技术根因：活动字段是平铺的，没有 system 层

**这是本次最重要的技术发现，我连错三轮才定位。**

```js
// ✗ 错（前三轮都这么写）—— a.system 是 undefined ⇒ 取到 {} ⇒ 读到的全是空
const sys = a.toObject().system;
sys.save    // undefined
sys.damage  // undefined

// ✓ 对 —— 字段平铺在活动对象顶层
const o = a.toObject();
o.save      // {"ability":["dex"],"dc":{"calculation":"spellcasting","formula":""}}
o.damage    // {"onSave":"half","parts":[{number:8,denomination:6,types:["fire"]...}]}
o.healing   // 治疗活动才有的键
```

**实测形状**（官方 `dnd5e.spells` 火球术）：

```
activities构造      = ActivityCollection
activities.contents = 数组，size = 1
活动构造            = MidiSaveActivity        ← midi 重写了活动类
a.system            = undefined               ← 根因
a.toObject() 键     = [_id, type, activation, consumption, description, duration, effects,
                       range, target, damage, save, uses, sort, name, img, flags, visibility,
                       useConditionText, useConditionReason, effectConditionText, macroData,
                       ignoreTraits, midiProperties, isOverTimeFlag, overTimeProperties,
                       otherActivityId, otherActivityAsParentType]
```

**⇒ 作废的四个数字**（它们测的是「我读不到」，不是「包里没有」）：
`save 缺 ability 525` ／ `伤害空 770` ／ `治疗空 97` ／ `scale 无定义 0`。

**⇒ 连带推翻的旧结论**：我上一轮曾说「官方 dnd5e.spells 火球/闪电束的 `save.ability` 同样全是 `{}`，
是官方写法」—— **那也是路径错了**。官方火球是 `["dex"]`，**不是 `{}`**。

### 正确判据（校准后）

| 项 | 正确写法 | 校准后计数 |
|---|---|---|
| save 活动的豁免属性 | `o.save.ability` 是数组且非空 | **0 件异常**（525 个 save 活动全部有值） |
| attack 活动的伤害 | `o.damage.parts` 空 **且** `includeBase:true` 是**官方正确写法**，伤害在物品级 `system.damage.base` | **0 件异常** |
| damage 活动的伤害 | `o.damage.parts[].number+denomination` **或** `.custom.enabled+formula` | 5 件待核 |
| heal 活动的治疗 | `o.healing.number+denomination` **或** `.custom.enabled+formula` | 8 件待核 |

**官方对照实证**（本包与官方逐字节一致）：

```
官方火球 damage = {"onSave":"half","parts":[{"number":8,"denomination":6,"bonus":"",
                   "types":["fire"],"custom":{"enabled":false,"formula":""},
                   "scaling":{"mode":"whole","number":1,"formula":""}}],"critical":{"allow":false}}
本包火球 damage = 与官方完全一致；两者 save.ability 都是 ["dex"]

官方长剑 attack damage = {"critical":{"bonus":""},"includeBase":true,"parts":[]}
本包血光长剑 attack    = 与官方完全一致
```

### ★ 这个包作者的一个特点

**大量使用 `custom.formula` + `@scale`/`@classes` 动态引用**，写法规范：

```
风暴之心   damage.parts[0].custom.formula = "floor(@classes.sorcerer.levels/2)"
           描述：「承受等于你术士等级一半的闪电或雷鸣伤害」          ⇒ 逐字对上
神圣打击    custom.formula = "@scale.cleric.divine-strike"
           描述：「额外造成 1d8 黯蚀伤害，第14级提升到 2d8」          ⇒ 对上
往生咒     healing.custom.formula = "max(@abilities.wis.mod + @classes.monk.levels,1)"
           types = ["temphp"]（临时生命）
           描述：「得到你的感知调整值+武僧等级的临时生命值（最小1点）」 ⇒ 逐字对上
时械矩阵   healing.custom.formula = "100"
           描述：「精魂合计提供至多回复100生命值」                    ⇒ 对上
```

**⇒ 这类「@scale/@classes 的真值」静态查不到，只有跑批才有 —— 这正是知识库 Q10 说的
「跑批不可替代的三件事」之一。**

## 六 · 判据演进（三轮修正，每一轮错在哪）

| 轮 | 判据 | 得出 | 错在哪 |
|---|---|---|---|
| 1 | `a.toObject().system.save` 是否为空 | save 缺 ability **525 件** | **路径错**（活动没有 system 层） |
| 2 | 同上 + `damage.parts` 是否为空 | 伤害空 **770 件** | 路径错 **+** attack 活动的 `parts:[]`+`includeBase:true` 是官方写法 |
| 3 | 补上 `custom.enabled && custom.formula` | damage 空 5 件、heal 空 8 件 | 判据基本对了 |
| 4 | CPR identifier 查不到 = 错误 | 39 件「错误」 | **前提丢了** —— 没先问「这件依不依赖 CPR」 |
| **5** | **先判自足性，再判 identifier** | **10 件真错误** | ✅ 当前采用 |

**教训**：把「我读不到」当成「数据没有」，是这套作业里最贵的错误。
**唯一可靠的校准方法 = 拿官方同结构样本逐字节对照**（官方火球 vs 本包火球）。

## 九 · 方法论沉淀

1. **活动字段平铺、没有 `system` 层** —— 读活动前先 `Object.keys(a)` 与 `Object.keys(a.toObject())` 各探一次。
2. **「官方也有同样的空」这句话要极小心**：我两次用「官方也是 `{}`」给误报开脱，两次都是**我读的路径错了**。
3. **判「缺实现」之前先判「自足性」**：有活动/效果/嵌入宏/macros 绑定 ⇒ 不依赖 CPR。
4. **`getMacro` 是 CPR 三源的统一入口**，返回 null 就是三源皆无；用它做对照实验
   （已知存在的 id 必须返回非 null）才能排除「工具本身不准」。
5. **CPR rules 由 `system.source.rules` 决定，不读 `flags.info.rules`** —— 在 info 里标 rules 没用。
6. **relay 的 execute-js 在严格模式下运行**：`xxx = {...}` 赋值未声明变量会报 `xxx is not defined`，**一律用 `const`**。
7. **`execute_js` 遍历 `game.packs` 时务必限定包名** —— 我写成「跳过 dnd5e_classpack」导致遍历 361 个包，
   请求排到超时（HTTP 408），把后续请求一起堵住。
