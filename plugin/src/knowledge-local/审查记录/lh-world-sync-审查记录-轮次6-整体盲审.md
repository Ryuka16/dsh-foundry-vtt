## 0. 本轮换了打法（为什么换）

用户原话：**「不是，我是说整体审查，你又开始一步一步做了，就会当局者迷旁观者清」**

前五轮全部是**改动专审**：我改了什么，就让审阅者去核什么。这仍然是作者视角——**我规定了他们看哪里**，看不见的东西永远不会被报告。

本轮改成三个**互不通气**的盲审视角，且**不给我已知的问题清单**（不给清单才不会框住视线）：

| 视角 | 任务 | Subagent |
|---|---|---|
| 冷读接手者 | 从零通读全部文件，判数据安全 / 状态一致性 / 失败处理 / 结构债 / 生命周期；并回答「只允许再改三处，指哪三处」 | `f050ae35-6716-4b45-8465-4d4ef2c4dd6b` |
| 文档对现实 | 先只读 README + module.json 建立预期，再逐条去代码核对「兑现 / 部分兑现 / 不兑现 / 无法确认」 | `e7a632ba-6c12-4e82-b912-1a3fc67175f4` |
| 对抗破坏者 | 模拟刷新 / 断网 / 双标签页 / 手改服务器文件 / 畸形导入 / 装卸模组，找「永久丢失 / 写坏世界 / 永久卡住 / 假防护」 | `54bb71c5-e308-40ce-8254-077ad2ec2baa` |

作者侧另做两件他们不会做的事：
1. **骨架统计**（不看单行，看同一件事有几条路径）——脚本统计关键函数的定义/调用点分布；
2. **服务器实测**——不带任何凭据直连用户公网服务器验证「快照是否可被外人读取」。

**关键收获：三路互不通气，却有两条结论完全相同，且与我骨架统计撞在同一点上。** 交叉印证的问题可信度最高。

## 1. 三路独立撞在同一点：同一类事实存了多份副本

> 接手者的原话：**「这不是『一个模块』，是『一个模块 + 一份逐年加固的防御工事』」**

真正的结构问题不是函数太长，而是四类事实各存多份：

| 事实 | 副本 | 位置 |
|---|---|---|
| 上次读取成功没有 | **5 个模块级变量** | `storageLastError`(`world-sync.js:501`，一写六读) / `applyLogReadError`(`:506`) / `legacyLogReadError`(`:511`) / `applyLogCorrupt`(`:515`) / `statusSnapCache`(`:2019`) |
| 操作互斥 | **3 套实现** | `withOpLock`(`:641-658`) / `applySnapshot`(`:1130-1142` + finally `:1241-1248`) / `rollbackApplyLog`(`:1278-1286` + finally `:1356-1358`) |
| 哪些键该写 | **4 套判据** | `diffSnapshot`(`:808`) / `plan`(`:1157-1179`) / `collectUnavailable`(`:1088`) / `isNsUnavailable`(`:1079`)，靠一句注释「必须共用同一个判据」(`:1066-1070`) 维系，无机制保证 |
| 失败后怎么还原 | **2 处近乎逐字重复** | `applySnapshot`(`:1211-1227`) 与 `rollbackApplyLog`(`:1313-1334`) |

**为什么这解释了历史**：六轮里 8 次「声称修了、实际只改了一半」，全部是「同一件事有 N 份副本，改了其中 M 份（M<N）」。这不是手滑，是结构必然——**只要副本还在，漏改就是默认结果**。

**接手者给出的「只允许再改三处」**：
1. **账本生命周期**（多代保留 + 写入完成标记 + 覆盖前明示）——唯一会造成不可逆损失处，约 60 行；
2. **`storageRead` 返回值结构化**（改为返回 `{text, error}`）——一处签名改动，一次性消灭 4 个跨调用全局状态与它们的全部错误归因（十几个调用点，机械改动）；
3. **统一 `withOpLock` + 统一结果对象**——消灭三套实现与三套文案，关掉「新增写路径就漏一处守卫」的结构性风险。

## 2. 【实测坐实】公网服务器上，任何人都能下载世界的全部配置

**这是本轮唯一「现在就在发生」的问题。**

### 实测（作者本人执行，无任何 Cookie / 凭据）

```
HEAD http://146.56.232.12:30000/modules/your-world-sync/module.json
  → 200  application/json  979 字节
HEAD http://146.56.232.12:30000/modules/your-world-sync/storage/world-snapshot-master.json
  → 200  application/json  9,268,088 字节   ← 8.8MB 全量 world 级设置
HEAD http://146.56.232.12:30000/modules/your-world-sync/storage/apply-log-chushi.json
  → 404（该世界暂无账本，非权限问题）
```

### 机制（接手者查证，`<FVTT安装目录>\resources\app\`）

`dist/server/express.mjs` 里数据目录是**整目录静态直出**：`e.use(express.static(this.paths.data,{redirect:!1}))`；它前面只有 locals、`Express.#a`（该函数只 `sessions.getOrCreate` 把 `req.user` 挂上，**不拒绝**）、CORS、扩展名黑名单（`.db`/`LOCK`/`LOG` 等）、压缩与缓存头——**没有任何登录门**。

写入侧：`world-sync.js:290` `STORAGE_DIR="modules/your-world-sync/storage"` + `:480` `FilePicker.uploadPersistent(MODULE_ID,"",...)`（`client/applications/apps/file-picker.mjs:505-513` 已核对，target=`${pack.type}s/${pack.id}/storage/${path}`）；读取侧 `:517` `foundry.utils.getRoute(...)` + `fetch`。

### 影响

- 快照含源世界**全部 world 级设置**（实测 1400+ 项）——而 world 级设置正是很多模块放 API key / token / 服务配置的地方；
- 账本 `apply-log-<worldId>.json` 里还有恢复前的同一批值；
- 玩家端同样可读（玩家本不该看到主世界的全部配置）；
- **这不是本模块的错**（Foundry 通用行为），但本模块**主动把全量配置写到那里**，等于把风险汇聚到一处。

### 处理方向（代码改不动，persistentStorage 只能落在 data 目录）

1. README 写明「快照是服务器上一个能被直读的文件，含全部 world 级设置」＋给出用完即删的指引；
2. 面板在「保存主快照」成功提示里加一句同等提醒；
3. （可选）给用户一段控制台脚本，一键列出 storage 目录里现存文件与大小，便于自查。

**待用户决策**：是否接受「文档化 + 提示」这一处理方式，或另有要求。

## 3. 会永久失去东西的两条（唯一真正不可逆）

### A1【最危险】恢复途中刷新 → 双互斥同时归零 → 撤销点消失 + 世界停在「从未存在过的中间态」

- **位置**：`world-sync.js:336-347`（`myOwner()`，存 sessionStorage）＋ `:560-570`（`_opInFlight`，页面内存变量）＋ `:587-590`（`sameOwner` 直接放行）＋ `:996-1008`（`writeApplyLog` 整格覆盖）＋ `:316-318`（注释自承千项级恢复常超 30 秒）
- **步骤**：恢复中按 F5 / 关标签重开 / 断网重连 → 新页面 6 秒后自动提醒弹窗（`:2301`）或手动再点恢复 → 两个 `applySnapshot` 并发
- **为什么必然失效（不是概率）**：`_opInFlight` 是页面内存变量，**刷新必然清零**；`myOwner()` 存 sessionStorage，**刷新必然不变** → 两道防线 100% 同时失效
- **后果三层**：
  1. 第二次 `writeApplyLog` 把 `store.worlds[wid]` 整格覆盖（`:996-1008`）→ 第一次恢复的 `prev`（**唯一撤销点**）永久消失；
  2. 第二次的 `prevMap` 取自已被改了一半的世界（`:1180-1184`）→ 账本记的是「半恢复态」→ 之后点回档，世界落到一个**从来没有存在过的中间状态**，而界面说「已回档 N 项，已还原」（`:1758-1760`）；
  3. 两次 `plan` 键集不同 → 第一次写过的键第二次可能不写，回档也不还原它们 → 世界停在两种状态的混合体。
- **全程零提示**：恢复执行期间界面没有任何进度反馈（报告弹窗是**完成之后**才出现的 `:1601/:1635`），而长时间无反馈时按 F5 是用户的默认反应。
- **与 README 承诺直接冲突**：README 声称同一会话 / 同一账号两个标签页的并发已被挡住。
- **修法建议**：① owner 拆两级——会话 id（sessionStorage）+ 每次页面加载生成的内存 token，放行条件收紧为「sameOwner **且** lock.token === 本页 token」→ 刷新后旧锁不再被认领并明确提示；② 写账本做成 CAS（把当前锁 operationId 写进账本，回读不一致即拒绝）；③ `_opInFlight` 加时间戳 + TTL 自愈；④ 恢复执行期间界面给进度并提示不要刷新。

### A2【严重】一次误存 + 下一次任意存 = 主快照与仅存备份两代全灭

- **位置**：`:294`（`MASTER_PREV_FILE` 固定名）＋ `:663-676`（`backupMasterSnapshot` 无条件覆盖、只保留一代）＋ `:2057-2083`（「存主世界」**无二次确认**）＋ `:712-732`（`buildSnapshot` 对条目数**无下限校验**）
- **步骤**：① 齐全世界存主世界 → master=完整快照，此时**还没有 .prev**；② 切到空世界/新世界再存 → master=那份残缺快照、.prev=完整快照；③ 再存一次（手滑或他人）→ `.prev` 被残缺 master 覆盖 → 完整快照在服务器上**再无任何副本**
- **后果**：全部 world 级配置永久失去，只能靠本地导出的 json 救
- **README 已承诺「点错还有退路」（:188），但退路只有一代且会被下一次保存摧毁**——防护存在，强度不够
- **修法建议**：① `.prev` 多代轮转（保留 5 份）；② 覆盖前做内容体检：读出当前 master 条目数 M，若本次 N 满足 `N < M*0.3` 或 `N < 20` 弹二次确认并写明「将用 N 项覆盖现有的 M 项」，N=0 直接拒绝；③ master 的 `sourceWorldId` 与当前世界不一致时并入同一条确认。

## 5. 三路排除的假警报（值得记，避免下次误报）

- `parseSnapshot` 的 `item.value === undefined`(`:765`) **不可达**——`JSON.parse` 不会为存在的属性产出 `undefined`；真正起作用的是上一行 `!("value" in item)`(`:764`)。`typeof item.value === "function"` 同理。
- `applySnapshot` 的 `if (e?.__notStarted) throw e;`(`:1203-1206`)——注释自己承认正常执行到不了。
- `nsIsUnavailable` 的 `n === MODULE_ID` 分支(`:1075`)——只为挡外部注入的 `precomputed`；正常路径已被 `:689` 与 `:773-775` 拦过。
- `FilePicker.upload` 失败时**不抛错**（`file-picker.mjs:454-461` 返回 false/undefined），本模块用 `if (!res?.path) throw`(`:486-489`) 兜住——**这层兜底有效**；但 `response.error` 那条会由 FilePicker 自己再弹一次（`notify:false` 只压住「无 path」那条）。
- `.json` 文件**覆盖写是被 Foundry 允许的**（`MEDIA_FILE_CATEGORIES` 含 TEXT，`common/constants.mjs`）——主快照/账本/锁的重复写入不会被拦，不是缺陷。
- `renderSidebar` 在源码里**没有字面量**，是由 `client/applications/api/application.mjs:1226-1233` 的 `#callHooks` 用 `"render{ClassName}"` 拼出、配合 `client/applications/sidebar/sidebar.mjs:23` 的类名 `Sidebar` —— 推断会派发（未实测）；即使不派发，8 次重试(`:2341-2350`)也能挂上按钮，故不算缺陷。
- **模块升级不会清掉用户的快照与账本**：`dist/packages/installer.mjs` 里声明了 `persistentStorage` 的包在更新时保留 `storage/` 目录（其余全删再解压）——module.json 的 `"persistentStorage": true` 是这条的前提，**别删**。

## 7. 本轮沉淀（写进方法论的部分）

1. **「注释替代码把活干完了」**——`:1934` 的注释写着「基准换了 → 面板状态栏缓存作废，**否则一直显示旧基准**」，但代码只清了缓存、没有重画状态栏。改动者用**意图**填平了实现缺口，读注释的人（包括下一轮的我）会以为已经做完。**规则：注释里凡是描述「用户会看到什么」的句子，都必须有一条断言守着它。**
2. **「两道防护互相取消」**——`_opInFlight`（页面内存，刷新清零）与文件锁的 `myOwner()`（sessionStorage，刷新不变）：单独看每个都合理，合在一起在「刷新」这个动作上**恰好同时归零**。**规则：互斥机制列出每一道的失效条件，检查它们是否会在同一个动作下同时失效。**
3. **「同一类事实多副本 → 漏改是默认结果」**——本项目六轮 8 次「修一半」的结构原因。**规则：发现同一件事有 N 处实现时，不要只修其中 M 处，要么合并成一处，要么在 N 处都留可被 grep 的同一标记。**
4. **工具坑**：同一份 LF 文件，`Get-Content` 报 1870 行、编辑器与 `read` 报 2400 行（**用 PowerShell 核对行号会整体偏小**，必须用 `read`/编辑器计数）。`Invoke-WebRequest` 设 `Range` 头会报 `The 'Range' header must be modified using the appropriate property or method`（需用 `-Headers` 之外的方式或直接全量 GET）。
