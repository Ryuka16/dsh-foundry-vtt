| 项 | 他的 | 我们的 |

## 一 · dnd5e 版本兼容警告（★ 本库的知识按 5.3.3 写）

**本资料库（reference 主题 / 手册 / 样本库）全部按 dnd5e 5.3.3 + Foundry 13.351 校准。**
如果你的世界是别的版本（例如 5.2.5），**套用前先用 `foundry_diff` 验一次** ——
5.2 → 5.3 之间字段结构变过，照抄会静默失败。

已知的具体差异（实测）：

- 5.3.3 的武器伤害骰在 `system.damage.base{number,denomination,bonus,types}`，活动里配 `damage.includeBase:true`
- 旧版（2014 规则结构）把骰子写在 `activities[].damage.parts[].formula` —— **在 5.3.3 里会被静默清洗掉，不报错**
- `save.dc.calculation` 的官方枚举是 8 项（`""` / `spellcasting` / 六属性），**没有 `flat`**

reference 主题里出现的「本机核对 5.2.5」标注是**取证来源说明**（我读的是哪个版本的源码），
**不是「5.2.5 也能这么写」的意思** —— 别读反了。

## 二 · 报错 → 原因 → 处置

| 报错 | 原因 | 处置 |
|---|---|---|
| `Script contains forbidden patterns` | execute_js 命中 relay 的 24 条黑名单（正则扫全文，注释里也算） | 本地预检已给行号，按行改；替代写法见 `foundry_reference{topic:"exec-js"}` |
| `Buffer is not defined` | 世界内没有 Node 的 Buffer（execute_js 跑在浏览器环境） | 别用 Buffer；base64 方案整体放弃 |
| `pack.index undefined` | compendium 包**尚未加载**（懒加载） | 先 `await pack.getIndex()` 或 `pack.getDocuments()` 再取；别直接读 index |
| `Entity not found: Item.xxx` | 传了裸 id 或错的 uuid 形式 | 世界物品 `Item.<id>`；**角色身上的 `Actor.<actorId>.Item.<itemId>`**；compendium `Compendium.<包>.<类型>.<id>` |
| `No connected Foundry clients found` | GM 浏览器不在线，或 relay 刚重启还没重连 | **先问用户「FVTT 开着吗」**；relay 重启后世界页面 **F5 才会重连**（实测：重启后一直报离线，F5 立即恢复） |
| `Request timed out`（408）但数据其实在 | **超时 ≠ 没执行** | 先回读确认，别直接重跑（会造重复文档） |
| `folder: must be a valid 16-character alphanumeric ID` | folder 传了 `Folder.xxx` 前缀 | 传纯 16 位 ID（本插件工具会自动剥前缀；手搓 JSON 时要自己剥） |
| 工具返回被拒 / `"value" must be an object` | 工具返回了裸数组，DSH 输出校验拒收 | 已修（返回统一包成对象）；老版本会遇到 |

## 三 · 读两次再下结论（★ 世界重载期读数不全）

**实测**：同一个世界的物品总数，一次读到 **675**，几分钟前是 **1008**。
不是「东西没了」，是**世界正在重载** —— collection 与 compendium 只加载了一部分。

**规矩**：数字比预期少时，**必须再读一次**（间隔十几秒），两次一致才下结论。
被判据误导过一次的代价，比多读一次大得多。

## 四 · 批量条数：环境差异（★ 我们俩不一样，别照搬）

| | 条数 | 环境 |
|---|---|---|
| 他的实测结论 | **≤6 条最稳**（3~6） | 470 个模块的本地世界 |
| 我们的默认值 | `foundry_create_batch` **默认 30 条 / 批间隔 90ms** | 204 个模块 |
| 我们实测过的上限 | 单次 `Item.create` 一次几百条会**静默返回 0**（世界一条没写，还不报错） | — |

**结论：没有普适数字。** 模块越多、世界越大，单批安全条数越小。

撞到 408 或静默 0 条时，**把 `batchSize` 往下调**（30 → 10 → 6），别一次调到最小（太慢）。
判据：跑完用 `foundry_search` 数一下实际落库数，**数量对不上就是批太大**。

## 五 · 大 payload 投递：两条路，环境决定走哪条

**问题**：超长内容（几万字符的子职描述、特性宏）直接塞进 `data` 会撑爆请求。

**他的做法（本地部署限定）**：本地写 JSON 到 `Data/_import_cards/<name>.json`
→ 世界内 `fetch('/_import_cards/<name>.json')` 读回来 → create。
他这样投过 **48,346 字符**的子职 + **12,207 字符**的特性。

**⚠️ 这条路依赖「你能往 Foundry 数据目录写文件」—— 云端部署走不通。**

**云端世界该走的**：**relay 自带 `/upload` 端点**（对应 `foundry_file_upload` 工具）
→ 上传到世界可访问的路径 → 世界内 `fetch` 读回 → create。
**云端、本地通吃，不依赖本地磁盘。**

**还有个更简单的选择：拆。**
把 48K 描述拆成几段分别写（`foundry_update_entity` 分段补 `system.description.value`），
比投递文件少一个环节、少一处失败点。**能用拆解决的，别上投递。**
