# 血的教训 · 建卡与升级授予篇

> 日期：2026-10-06 晚｜环境：Foundry 13.351 / dnd5e 5.3.3 / midi-qol 13.0.55 / CPR 1.5.15 / DAE 13.0.25 / AC5E 13.5330.1.2
> 场景：`dnd5e_classpack` 模块包（21 个包）批量建卡（391 张验收卡）后，用户人工抽查发现的 5 类问题
> 为什么有这篇：**advancement（升级授予）是「卡上为什么会多东西/少东西/重复东西」的唯一源头**。
> 之前所有资料都在讲「物品怎么做活动」，没人讲「物品怎么被发到卡上」——这一篇补这一块。

---

## 〇、只读十条（最贵的）

1. **dnd5e 5.3.3 只有 8 种 advancement 类型，没有「替换已有物品」这一种** —— 但 `ItemChoice` **自带**替换机制。
2. **`replacement: true` + `count: null` = 「纯替换级」** —— 那一级不给新东西，只让玩家把之前选的换掉。这是 TCE「替换武术」的正解。
3. **`ItemGrant.optional` 只有「真拖入」这条路径会弹复选框** —— `apply(…, {initial:true})` 会**忽略 optional 且覆盖 selected**，用它验证拖入行为必然得出错误结论。
4. **`consumption.targets` 写 UUID 会坏、写 identifier 能活** —— 根因是 `_remapConsumptionTarget` 只在「当前 actor」上找物品（详见 `血的教训-CPR脱钩与消耗目标篇.md` 第五节，本篇第七节补本轮数据）。
5. **不能用 `d.system.advancement` 读结构** —— 它是 `AdvancementCollection`，`Object.keys()` 恒为 0；必须 `d.toObject().system.advancement`。
6. **批量 API 建出来的卡会「僵尸化」** —— `actor.items.get(id)` 说存在，`update()`/`delete()` 报 `Item "xxx" does not exist!`。改不动就是改不动，别在那上面耗时间，重拖即好。
7. **advancement 是 ObjectField，`update` 是合并不是替换** —— 必须用 `"system.advancement.-=<旧键>": null` 显式删旧键。
8. **升级管理器里的每一项都可以 `reverse(level)` 撤销** —— 所以「选错了能不能反悔」这个问题的答案永远是「能」。
9. **「给一个描述性文字物品」不是自动化** —— 包里那 6 件「替换武术/魔能选项/…」全是 0 活动 0 效果的纯文本，玩家看不懂也换不了。
10. **判断「描述⇄实现是否对得上」的判据必须同构** —— 中文自然语言 ⇄ 程序结构的两条路（见第十节），本项目为此白写了 193 条错误标注。

## 一、dnd5e 5.3.3 只有 8 种 advancement 类型

实测 `CONFIG.DND5E.advancementTypes`：

```
AbilityScoreImprovement   属性提升（ASI）
HitPoints                 生命值
ItemChoice                选物品（可重复选 + 可替换）
ItemGrant                 给物品
ScaleValue                数值缩放（apply 是空函数，不用调）
Size                      体型
Subclass                  子职业
Trait                     特性/熟练/语言
```

**⇒ 没有「移除物品」「替换物品」这一种类型。**

**`allowReplacements` 只存在于 `Trait` 的 schema**，管的是 Trait 自己的选择（技能/语言/熟练），**跟物品无关**：

```js
// Trait.automaticApplicationValue
async automaticApplicationValue(level, { initial }={}) {
  const { available } = await this.unfulfilledChoices();
  const chosen = new Set();
  for ( const { choices } of available ) {
    const set = choices.asSet();
    if ( set.size === 1 ) chosen.add(set.first());
    else if ( !initial && ((set.size > 1) || this.configuration.allowReplacements) ) return false;  // false = 弹框让玩家选
  }
  return { chosen: Array.from(chosen) };
}
```

## 二、★★★ `ItemChoice` 的 `replacement` —— 原生「替换」机制（本篇核心）

### 2.1 UI 侧：radio 按钮（dnd5e 自带）

```js
// ItemChoiceFlow（dnd5e.mjs，实测原文）
} else if ( event.target?.type === "radio" ) {
  if ( event.target.value ) await this.advancement.apply(this.level, { replace: event.target.value, previousItems: this.retained });
  else await this.advancement.reverse(this.level, { clearReplacement: true, previousItems: this.retained });
}
```

**⇒ 玩家在升级框里看到一组 radio，选中一个 = 「把那个旧的换掉」；不选 = 保持原样。**

### 2.2 执行侧：真的从卡上删掉旧物品

```js
// ItemChoiceAdvancement.apply
async apply(level, { previousItems, replace: original, retainedData={}, ...data }, options={}) {
  let replacement;
  if ( retainedData.replaced ) ({ original, replacement } = retainedData.replaced);

  await super.apply(level, { ...data, retainedData }, options);

  if ( original ) {
    const replaced = this.value.replaced[level] ?? {};
    await this._restoreReplacedItem(replaced.level, replaced.original, previousItems ?? retainedData.items);
    const replacedLevel = Object.entries(this.value.added).reverse().reduce((level, [l, v]) => {
      if ( (original in v) && (Number(l) > level) ) return Number(l);
      return level;
    }, -Infinity);
    if ( Number.isFinite(replacedLevel) ) {
      this.actor.items.delete(original);        // ★★★ 这里：旧物品真的从卡上消失
      this.actor.reset();
      this.updateSource({ [`value.replaced.${level}`]: { level: replacedLevel, original } });
    }
  }

  const replaced = this.value.replaced[level];
  if ( replaced && !replaced.replacement ) replacement ??= options.firstCreatedItem
    ?? (this.getCounts(level).full ? Object.keys(this.value.added[level] ?? {})[0] : undefined);
  if ( replacement ) this.updateSource({ [`value.replaced.${level}`]: { replacement } });

  await this._evaluatePrerequisites(level, { showMessage: true });
}
```

**⇒ 完全对应「放进卡里就删除或者覆盖上一个、卡里不乱」这个诉求 —— 它是原生行为，不用写宏。**

### 2.3 数据侧：开关就在 `choices`

```json
"configuration": {
  "choices": {
    "1":  { "count": 2,    "replacement": true  },   // 给 2 个，之后可替换
    "4":  { "count": null, "replacement": true  },   // ★ 纯替换级：不给新的，只让换
    "10": { "count": 1,    "replacement": false }    // 再给 1 个，不容替换
  }
}
```

**判据：**
| `count` | `replacement` | 含义 |
|---|---|---|
| 数字 | `false` | 普通授予级（选 N 个，不能换） |
| 数字 | `true` | 授予级 + 允许以后替换 |
| `null`/缺省 | `true` | **纯替换级**（那一级只在升级框里提供替换选项） |
| `null`/缺省 | `false` | 无意义（不授予也不可换） |

`configuredForLevel` 的判据印证了这一点：
```js
configuredForLevel(level) {
  return (this.value.added?.[level] !== undefined) || !this.configuration.choices[level]?.count;
}
// count 为空 ⇒ 直接返回 true ⇒ 视为「已配置」，不需要玩家操作
```

### 2.4 撤销

每个 advancement 都有 `reverse(level, { clearReplacement, previousItems, ... })`：
```js
async reverse(level, { clearReplacement, previousItems, retainedData={}, skipEvaluation, ...options }={}) {
  const replaced = this.value.replaced[level];
  const restoreReplacedItem = replaced && ...;
  if ( restoreReplacedItem ) {
    retainedData.replaced = replaced;
    await this._restoreReplacedItem(replaced.level, replaced.original, previousItems ?? retainedData.items);
  }
  if ( replaced && foundry.utils.isEmpty(options) ) {
    this.updateSource({ [`value.replaced.-=${level}`]: null });
  ...
```
**⇒ 玩家反悔时旧物品会被恢复。所以「替换」不是单向操作。**

给对应 ItemChoice 的 `choices` 补上纯替换级：

```js
    "4":  { count: null, replacement: true },
    "8":  { count: null, replacement: true },

    "16": { count: null, replacement: true },
    "19": { count: null, replacement: true }
  }

```

**⚠️ 改前必须做的三件事：**
1. **先备份旧 `choices` 全量**（本项目硬约束：改前值落盘备份）。
2. **改一件 → 建一张该职业的 L3 测试卡 → 升到 L4 → 看升级框里有没有 radio** —— 不实跑不算数（源码读通了也可能 UI 不弹）。
3. **确认对「已建好的老卡」无害** —— 老卡的 `value.added` 已存在，加纯替换级不会追溯删东西。

## 六、`ItemGrant` 的 `optional` 与两条路径的差异（关键坑）

### 6.1 三次实测：`optional` 两个值都不等于「二选一」

| 配法 | 用 API `createEmbeddedDocuments` 拖入的结果 |
|---|---|
| `optional: false` ×2（原值） | 给 2 件 —— 两个都给 |
| `optional: true` ×2 | 给 **0** 件，且**不弹任何框** |
| 换成 `ItemChoice`（原生「选 N 个」） | 给 **0** 件，也不弹框 |

### 6.2 ★★ 两条路径行为完全不同

```js
// 路径 A：手动/宏调用
await adv.apply(0, {}, { initial: true });                        // 给 2 件（忽略 optional）
await adv.apply(0, { selected: [一个uuid] }, { initial: true });   // 仍然给 2 件 ← initial 覆盖 selected

// 路径 B：dnd5e 自己的表单流程（玩家真拖入走这条）
// ItemGrantFlow._handleForm 的 else 分支：
const selected = cfg.items.filter(i => !cfg.optional && !i.optional).map(i => i.uuid);
if ( selected.length ) await adv.apply(this.level, { selected });
```

**⇒ 结论：`initial: true` 下 `optional` 被忽略；只有不带 `initial` 的 `selected` 路径才尊重 optional。**
**⇒ 因此「API 建 item 后手动 apply」不能用来验证真拖入行为 —— 必须让玩家真拖一次。**

### 6.3 看门狗相关的模板源码（`item-grant-flow-v2.hbs`）

```handlebars
{{#if optional}}
    <dnd5e-checkbox name="{{ uuid }}" {{ checked checked }}></dnd5e-checkbox>
{{else}}
    <input type="hidden" name="{{ uuid }}" value="true" data-dtype="Boolean">
{{/if}}
// JS: item.optional = config.optional || i.optional;
```

**⇒ `optional: true` 的项在升级框里渲染成复选框，玩家可以勾/不勾 —— 这就是「正常弹」的正解。**

### 6.4 本包已按此修过的两处

- **5 个背景的变体特性**（海盗/水手/博德之门水手/贵族/博德之门贵族）：基础款保持 `optional: false` 自动给，变体（恶名/家仆/宗贵）设 `optional: true` 让玩家勾。
  - 规则书依据：`00_规则资料\5E 不全书-纯文本\玩家手册\个性与背景\水手.txt:155,163`、`贵族.txt:161,163,169`（官方术语叫**变体特性**）。
  - **骑士 Knight 不改** —— 规则书明说「选择骑士背景则使用家仆代替特权地位」（`贵族.txt:161`），它本来就该只给家仆。
- **6 个职业的可选特性**（替换武术等）：游侠原本 `optional: false`，改成 `true`；其余 5 个本来就是 `true`。

**⚠️ 判据要先按「特性 grant」筛**：`title` 含「特性」+ `configuration.items.length >= 2` ⇒ 13 条命中，其中 4 条是**装备**被误标了 title「获得背景特性」，不分清就会全误报。

## 八、僵尸物品：批量 API 建卡的必然后果

**现象（实测，两条删除路径全失败）：**
```js
const it = actor.items.get("HhyVN6IIStU6CwAc");   // ← 拿得到
await it.update({ "system.activities": acts });    // ✗ Cannot read properties of undefined (reading 'id')
await it.update({ "system.activities.dnd5eactivity000.consumption.targets": [...] }); // ✗ 同上
await it.delete();                                 // ✗ Item "HhyVN6IIStU6CwAc" does not exist!
await actor.deleteEmbeddedDocuments("Item", [id]); // ✗ 同上
// relay 工具 foundry_delete_entity(Actor.<id>.Item.<id>)  // ✗ 同上
```

**矛盾点：** `actor.items.get(id)` 说有、`toObject().items` 里也有（139/139 唯一 id、无重复），但 update/delete 都报「不存在」。

### 8.1 ★★★★★ 根因（2026-10-07 更正，前一版写的是错的）

**旧版写的是「内存集合与文档层不一致」—— 不对。真根因是：**

> **`advancement.apply()` 只改内存，真正的落库由「升级向导」（`AdvancementManager`）在最后统一提交。**
> 绕过向导直接调 `apply()` ⇒ 客户端看着完整、服务器从来没收到过这些物品。

**铁证（同一次会话内做出的对照实验）：**
```
方式A · createEmbeddedDocuments 直接建   → 更新/删除全部通过 ✓
方式B · advancement.apply() 建的        → 报 "Cannot read properties of undefined (reading 'id')" ✗
```
**关键：当场新建、当场探测就坏** —— 不是「后来坏的」，是**从来没落库**。

**服务器端堆栈（这是判定「服务器收没收到」的唯一硬证据）：**
```
TypeError: Cannot read properties of undefined (reading 'id')
  at .../resources/app/dist/database/backend/server-backend.mjs:1:5431
  at Array.map (<anonymous>)
  at ServerDatabaseBackend._updateDocuments (server-backend.mjs)
  at async #try (.../common/utils/semaphore.mjs:98:17)
```
删除时走另一条路，报：`Item "<id>" does not exist!`（来自 `ServerDatabaseBackend._deleteDocuments`；升级向导里的调用栈是 `advancement-manager.mjs:929` ← `#complete @ :915` ← `#forward @ :718` ← `#process @ :652`）。

**四种删法全失败**（补测）：`t.update({...})` / `t.delete()` / `a.deleteEmbeddedDocuments("Item",[id])` / `a.update({"items.-="+id})` —— 最后一种不报错，但物品仍在。

**判定用的真值探针（原值写回是假探针，别再用）：**
```js
// ✗ 假探针：原值写回，空操作可能被短路，服务器根本不校验
await t.update({ "system.source.custom": 原值 });
// ✓ 真探针：改成不同值再改回，净零改动但确实发出两次请求
try { await t.update({ name: 原名 + "~" }); await t.update({ name: 原名 }); 状态 = "好"; }
catch (e) { 状态 = "幽灵"; }
```

### 8.2 ★★★★★ 第二个 id 坑：`createEmbeddedDocuments` 必须传 `{ keepId: true }`

**现象：** 改用「影子卡算、真卡收」之后物品落库了，但**替换时旧物品仍然删不掉**。
**原因：** `createEmbeddedDocuments` **默认不保留传入的 `_id`**（服务器重新生成）⇒ 而 advancement 里 `value.added` 的键、`flags.dnd5e.advancementOrigin` 前缀还指着旧 id ⇒ **两边对不上**。

## 十、写作纪律：判据必须同构（193 条错误标注的由来）

### 10.1 事故

**上个会话往 `dnd5e_classpack` 里批量写入了 `【自动化无法匹配】` 标注共 193 件**（另有「人工确认」79 件、「无法自动化」10 件）。
用户看后原话：**「物品描述里是你写的，上一个接受的会话，他查证的很显然不彻底，所以自动化文字都不咋可信」**

**抽查即可证明用户是对的**（对照项目资料库 `foundry_reference{topic:"roll-data"}`）：
- 「超限导能」标注「拿不到本次用了第几环」 —— 但 `@scaling / @scaling.increase / @item.level` 都是**合法引用**
- 「法术轰击」标注「无按骰面触发的一次性加骰机制」 —— 未核 midi 侧
- 「魔能祈唤:饥渴魔刃」标注「属攻击次数规则，无字段」 —— 未核 midi 的 attacks
- 「威慑之姿」标注「无法按目标计数」 —— 未核 DAE 的 `stackable`
- 「拨挡飞弹(反弹)」标注「减伤无字段」 —— 未核 `traits.dm` / midi 减伤
- 「图腾精魂-虎」标注「movement.jump 是派生值」 —— 未核其他落点

### 10.2 为什么自动判据会连续误报（五次实测记录）

| 判据 | 规模 | 结果 |
|---|---|---|
| ✅ 描述时长词 ⇄ 活动 duration | 全库 | 12 件可疑 → **3 件真错**（风暴之盾×3 / 繁星形态×2 / 怠惰之枪）已修 |
| ✅ 描述 +N ⇄ changes 数字 | 86 件 | **全部一致，0 疑点** |
| ✅ 字段类型 ⇄ mode 2 | 1203 个 mode 2 | **1 件真错**（龙族体魄 ac.calc）已修 |
| ❌ 描述机制词 ⇄ changes 键名 | — | 30 条疑点，抽查**全是误报** |
| ❌ 描述机制 ⇄ 活动/效果存在性 | — | 30 条仍以误报为主（触发条件被当成效果承诺） |
| ❌ 描述状态名 ⇄ statuses | 299 件 | 报 245 件没实现（82%）—— 误报为主 |
| ❌ 描述骰子 ⇄ 数据骰子 | 477 件 | 报 73% 缺失 —— 描述里的骰子是**等级表** |
| ❌ 描述数值增益 ⇄ 实现 | 228 件 | 报 90% 缺失 —— 机制**跨物品**组合 |

**⇒ 规律：成立的三条都是「单值声明 → 单值事实」；失败的五条要么需读懂中文，要么机制跨物品。**

### 10.3 结论（写进流程）

1. **判据必须同构**：自然语言 ⇄ 程序结构之间没有可靠映射，别硬凑。
2. **做单向包含检查，不做双向 diff**：`描述的关键声明 ⊆ 实现`。因为第三方补自动化的实现**几乎总是比描述多**，反向检查全是误报。
3. **检查目标是「目标最终 statuses 集合」而不是「源 effect 的 statuses」** —— AC5E 会把条件补到**第二个效果**上（实测：征服威压源 effect 只有 `macro.StatusEffect=frightened`，完整劣势条件在 AC5E 补的第二个效果里）。
4. **同义词表不要自己造** —— 汉化环境下 `CONFIG.DND5E.conditionTypes` 就是「中文状态名 → key」的现成权威映射。
5. **没有硬特征就不要自动扫**：「type 是 undefined」扫得出；「缺内容」只能人眼。
6. **标注「做不到」之前必须先查证** —— 写进包里的每一句「无法匹配」都是**给玩家的承诺**，写错了就是骗人。

### 10.4 已被证明可靠的三类静态扫描

1. **引用断链**：活动 `effects[]._id` 是否指向真实存在的效果 ⇒ 本轮 7 包 **0 件**。
2. **真空壳**：有活动无效果无宏 ⇒ 本轮 **1 件**（`moditems`·压缩空气 Bottled Breath 的「无需呼吸」）。
3. **CPR 规则版本错配**：`system.source.rules='2014'` 但宏只在 modern 表 ⇒ 本轮 **9 件**。

**⚠️ CPR identifier 判据的边界（犯过两次）：**
- **「identifier 在 CPR 表里查不到」不能直接判错** —— 必须先问「这件到底依不依赖 CPR」。
- **正确判据**：有活动 ∨ 有效果 ∨ 有嵌入宏 ∨ 有 macros 绑定 ⇒ 实现自足 ⇒ CPR 断链只是少了加成；四条全无 ⇒ identifier 查不到才是真错误。
- **`activityIdentifiers` 的键是「CPR 内部活动名」，不是宏 identifier** —— 拿它去 `getMacro()` 查必然报缺失（第一轮 103 个「缺失」里混的就是这批假货）。
- **`getRules(entity)` 对 Item 读 `system.source.rules`（`''`/`'2014'`→legacy，其他→modern），不读 `flags.info.rules`** —— 在 `info` 里标 rules 没用。

**配套源码（dnd5e.mjs）：**

```js
getCounts(level) {

  const max = (this.configuration.choices[level]?.count ?? 0) + (replacement ? 1 : 0);
```

### 12.3 修法（已执行，110/110 成功）

**思路**：把 faux 换成**真实法术 uuid**。建索引：拿「包内 `dnd5e_classpack.spell` 545 条 + 官方 `dnd5e.spells`」的名字（**去掉中文只留英文部分**）和 `system.identifier` 做 key，再去匹配 `{"tag":"spell","text":"<name>"}` 里的 name。

```js
// 取包内文档要 getDocuments（getIndex 拿不到 activities）
const d = await pack.getDocument(id);
const o = JSON.parse(JSON.stringify(d.toObject()));
const acts = o.system.activities || {};
acts[活动键].spell.uuid = 真实uuid;
await d.update({ "system.activities": acts });   // ★ compendium 改集合没用，必须逐文档 update
```

**结果**：110 件全改、失败 0、剩余坏件 0、改前值备份 285 条、读回复查 0 处残留。

### 12.5 全库引用型字段清单（下次扫断链照这张表）

|---|---|---|
| 活动 | `effects[]._id` | 同物品的物品级 effects |
