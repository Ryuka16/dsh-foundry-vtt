## 0. 血的教训（最重要，先看这六条）

1. **污染有六个源，不是一个。** 清了一个不等于清了。我们花了三轮才把六个源找齐：
   模板预览容器 / **网格高亮 GridHighlight** / Sequencer 持留特效 / 召唤物 token / Region / 画布裸 Graphics。
   **每清掉一个，用户屏幕上还在的东西就会指向下一个源。**

2. **「清不掉」的往往根本不是文档，是渲染层对象。**
   用户说「我删不掉他」，因为那东西**不在模板工具的选择范围里** —— 它不是 MeasuredTemplate 文档，是挂在 `canvas.interface.grid` 里的一个 `GridHighlight`，
   名字叫 **`MeasuredTemplate.null.preview`**（名字里的 `null` 就是线索：它没有对应文档）。
   **⇒ 排查第二源时，不要只查 `canvas.scene.templates`（那是文档层），要查 `canvas.stage` 全树的渲染对象。**

3. **弹框看门狗只认 `button[type="submit"]` 会漏掉一半框。**
   midi 的两类框 —— `MidiActivityChoiceDialog`（选豁免/伤害）和 `MidiActivityUsageDialog`（配置框，里面有一行字面叫「放置测量模板」）——
   它们的按钮是 **`type="button"` + `data-action="choose"` / `data-action="use"`**，**一个都不匹配 submit 判据**。
   ⇒ 看门狗全程对它们失明，框一个个攒在用户屏幕上，直到用户手动点。

4. **框没人点 ⇒ `use()` 永不 resolve ⇒ 看起来像「活动卡死」，其实是「没人点框」。**
   实测反证：同一批 6 件，旧判据下 0/6 完成、耗时全是 `8001~8006ms`（**没有任何中间值 = 只是在干等超时器**）；
   换成新判据 + 完整压制配置后 **5/6 完成、中位 520ms**。
   > ⚠️ 但注意：`use()` 返回的是**真 Promise**（6/6 实测），所以「它确实卡住了」是成立的；
   > 只是**卡的原因是等框，不是活动本身有问题**。

5. **会「等玩家放模板」的活动是唯一清不干净的：它的流程活着，你清一次它画一次。**
   实测：跑批收尾清场明明清了 3 段高亮，**收尾后复查仍是 24 段** —— 因为那一件的 `use()` 还挂在「等模板」状态，
   持续往画布上重画。**这不是清理失败，是流程还在跑。**
   ⇒ 与第 2 条合起来就是用户看到的「删都删不掉，清完又出现」。

6. **别把「默认路径能跑」当成「交互活着」。**（同族教训，见 DialogV2 篇）
   本文的看门狗永远点同一个选项（优先 `data-action="normal"`），**这是固定路径，不等于覆盖了所有分支**。
   跑批验证只证明「这条路走得通」，不证明「所有选项都对」。

## 1. 六个污染源全清单（每个都要清）

> **通用排查动作**：清完一轮后 → **等 1~3 秒再复查一次**。
> 如果东西又回来了，说明**要么还有没清的源，要么有活着的流程在重画**。这一条是判断「清没清干净」的唯一可靠方法。

### 1.1 模板预览容器（第一源，最显眼）

| | |
|---|---|
| **现象** | 鼠标上跟着一个模板轮廓（圆圈/锥形/线形） |
| **判据** | `canvas.templates.preview.children.length > 0` |
| **清理** | `canvas.templates.preview.removeChildren()` |

```js
// 注意：canvas.templates.clearPreview 实测是 undefined，不能调
try { if (canvas.templates.preview && canvas.templates.preview.removeChildren) canvas.templates.preview.removeChildren(); } catch (e) {}
```

**⚠️ 只清这个是不够的 —— 它只清「预览容器」，画格子的高亮在另一个对象里（见 1.2）。**

---

### 1.2 ★ 网格高亮 GridHighlight（第二源，最隐蔽 —— 2026-10-06 新发现）

| | |
|---|---|
| **现象** | 一块**规整的色块**（矩形/十字/圆），怎么删都删不掉；鼠标移动时闪 |
| **为什么删不掉** | 它**不是文档**（不是模板、不是图块、不是 Region），是画在 `canvas.interface.grid` 里的一个**逐格高亮图层**。模板工具、区域工具都选不中它 |
| **为什么像一整块** | 它是**一个格子一个格子描出来的**，40 个格子连起来看起来就是一块矩形。默认高亮色是暗红/红褐 |
| **判据** | 遍历 `canvas.stage` 全树，找 `constructor.name` 含 `GridHighlight` 且 `geometry.graphicsData.length > 0` 且 `visible !== false` 的对象 |
| **对象名线索** | **`MeasuredTemplate.null.preview`** —— 名字里带 `MeasuredTemplate` 而 document 是 `null`，说明它是「模板预览的残留高亮」 |

```js
// 探测：数出当前有多少段高亮，并打印名字
function 读高亮() {
  let 段 = 0; const 名 = [];
  const 走 = (n, d) => {
    if (d > 8 || !n || !n.children) return;
    for (const c of Array.from(n.children)) {
      try {
        if (((c.constructor || {}).name || "").indexOf("GridHighlight") > -1) {
          const g = (c.geometry && c.geometry.graphicsData) ? c.geometry.graphicsData.length : 0;
          if (g > 0 && c.visible !== false) { 段 += g; 名.push(String(c.name || "?")); }
        }
      } catch (e) {}
      走(c, d + 1);
    }
  };
  走(canvas.stage, 0);
  return { 段, 名 };
}

// 清理：全部 clear（纯视觉层，不碰任何数据）
function 清高亮() {
  let k = 0;
  const 走 = (n, d) => {
    if (d > 8 || !n || !n.children) return;
    for (const c of Array.from(n.children)) {
      try { if (((c.constructor || {}).name || "").indexOf("GridHighlight") > -1 && c.clear) { c.clear(); k++; } } catch (e) {}
      走(c, d + 1);
    }
  };
  走(canvas.stage, 0);
  return k;
}
```

**实测数据（2026-10-06）**：
- 触发前提：跑「带模板的活动」（锥/线/球/立方/圆柱/墙）后
- 每件跑完读一次：**4 段**（含正常完成的件 —— 所以**不是「卡了才留」，是「碰过模板就留」**）
- 清一次 → **0 段**；等 1 秒复查 → **仍 0 段**（流程已结束时）
- 但若流程还活着（等模板中）→ 收尾清了 3 段，**复查 24 段**（被重画）

> **⇒ 结论：清理必须「每件跑完清一次」+「收尾清一次」+「收尾后延迟 2~3 秒再清一次」。**

### 1.5 Region（第五源）

| | |
|---|---|
| **现象** | 红色圆形/矩形区域，**模板工具选不中、右键无删除项** |
| **实例** | 跑「火墙术」→ CPR 拦截 → 建 2 个 Region，名 `火墙术 Wall of Fire` / `火墙术 Wall of Fire 火焰`，带 `flags["chris-premades"].wallOfFire.casterUuid` 指向施法者 |
| **判据** | **不能用 `_stats.createdTime`（实测返回 null）**，要用**跑前快照 diff** |
| **清理** | `for (const rg of canvas.scene.regions.contents) { if (跑前快照[rg.id]) continue; await rg.delete(); }` |


**⚠️ 注意 `canvas.regions.placeables` 也要查**（渲染层）；实测正常时 `placeables.length === 0`。

### 1.6 画布裸 Graphics（第六源）

| | |
|---|---|
| **现象** | 红色大圆圈 / 矩形，**不是文档**，是某个宏（实测是 CPR 的 `wallOfFire`）持续往 `canvas.stage` 画的 |
| **判据** | `canvas.stage` 的直接子节点里，**类名不以 `CanvasGroup` 结尾**的 |
| **清理** | 逐一 `parent.removeChild` + `destroy({children:true})` |

```js
// ⚠️ 必须跳过 /CanvasGroup$/ 的标准组，否则会把画布拆了
try {
  let n = 0;
  for (let i = canvas.stage.children.length - 1; i >= 0; i--) {
    const sc = canvas.stage.children[i];
    const sn = (sc.constructor && sc.constructor.name) || "";
    if (/CanvasGroup$/i.test(sn)) continue;
    try { sc.parent.removeChild(sc); try { sc.destroy({ children: true }); } catch (e2) {} n++; } catch (e) {}
  }
  if (n) 出.清画布裸图形 = n;
} catch (e) {}
```

**实测**：标准组有三个 —— `HiddenCanvasGroup` / `RenderedCanvasGroup` / `OverlayCanvasGroup`（全部以 `CanvasGroup` 结尾）。

**判据表：**

| 观察 | 结论 |

## 4. 让活动「别停下来等人」的压制配置（跑批必设）

**实测：加了这一套之后，同一批从 0/6 完成变成 5/6 完成。**

```js
const 改 = {}; const 活动 = 副.toObject().system.activities || {};
for (const k of Object.keys(活动)) {
  改["system.activities." + k + ".consumption.targets"] = [];      // 清掉「消耗目标」
  改["system.activities." + k + ".consumption.spellSlot"] = false;  // 清掉「消耗法术位」
  改["system.activities." + k + ".target.prompt"] = false;
  改["system.activities." + k + ".target.affects.choice"] = false;  // ★ 否则弹 targetConfigurationDialog
  改["system.activities." + k + ".midiProperties.autoTargetAction"] = "none";
  改["system.activities." + k + ".midiProperties.forceRollDialog"] = "never";
  改["system.activities." + k + ".midiProperties.forceConsumeDialog"] = "never";
  改["system.activities." + k + ".midiProperties.forceDamageDialog"] = "never";
  改["system.activities." + k + ".midiProperties.forceConfigDialog"] = "never";
}
await 副.update(改);
```

**⚠️ 文档情况**：`forceConsumeDialog` 这类键名 **midi 官方 FLAGS.md（75KB）和 README（66KB）里都没有**，
它们只存在于 midi 的设置界面。实测这些键确实生效（框被压掉），但**别指望在文档里查证**。

**⚠️ 另一条实测**：这些压制键**压不住「放模板」**。放不放模板由活动的 `target.template.type` 决定，

## 5. 唯一的硬骨头：会「等玩家放模板」的活动

### 5.1 现象与机制

- 活动带模板（`target.template.type` 非空）⇒ `needTemplate` 为 true ⇒ 流程停下来等玩家在图上点一下
- 或者：`cast` 活动**调用的那个法术**带模板（例：噬烟流 → 火墙术）⇒ **它自己的活动列表里一个模板都没有，照样卡**
- 卡住期间：**鼠标上有模板轮廓 + 画布上有高亮，且清一次画一次**（流程活着）

### 5.2 规模（实测，13 个包全量）

| 形状 | 件数 | 要不要选方向 |
|---|---|---|
| radius / sphere / cube / cylinder / square / circle | 330 | 只要位置 |
| **cone / line / wall** | **106** | **要选方向 ★** |
| 合计（件级去重） | **436** | — |

带模板活动总数 **493** 个。全部包合计：**带模板件的 358 件（占有活动件的 13.3%）**。

### 5.3 三条被实测否掉的路（**别再试**）

| 方案 | 结果 |
|---|---|
| **清空副本的 `target.template = {}`** | ❌ dnd5e 的 `TargetField` 会**重建回 cone/wall**，落库仍是 `["cone","cone"]`，`needTemplate` 仍 true |
| **手建 `MeasuredTemplate` + 调 `processPlacedTemplates`** | ❌ 模板被接受（tpl 0→1、needTemplate false），**但流程不动** |
| **在框里「取消勾选」放置测量模板** | ❌ **框根本不弹**（被 `forceConfigDialog:"never"` 压掉了）⇒ 没有勾可取消 |

### 5.4 还能走的路

1. **跳过这类件**（可靠，但漏验）—— 判据：活动或其 `cast` 目标带 `target.template.type`
2. **★ 超时后「延迟 600ms 再补清一次高亮」（2026-10-06 四轮对照实验定案，已验证）**

   **先记一条被推翻的错误线索**（写在这里防后人再踩）：
   > 曾观测到「跑批收尾清了 3 段，复查仍 24 段」vs「手动清理（顺手删了物品副本）后 0 段」，
   > 于是推测「**删掉物品副本能止住悬挂流程**」。
   > **四轮对照实验（A 组不删副本 ×2 / B 组删副本 ×2）结果显示：删不删，结果完全一致。**
   > ⇒ **该推测已撤回。删副本与此无关。**

   **四轮实测数据（唯一变量 = 超时后是否删物品副本）：**
   ```
   A-不删 | 超时9002ms | 超时后高亮24 | 清3处 | 清后0 | 3秒后0 | 不重画
   B-删副本| 超时9003ms | 超时后高亮24 | 清3处 | 清后0 | 3秒后0 | 不重画
   A-不删 | 超时9003ms | 超时后高亮24 | 清3处 | 清后0 | 3秒后0 | 不重画
   B-删副本| 超时9001ms | 超时后高亮24 | 清3处 | 清后0 | 3秒后0 | 不重画
   ```

   **⇒ 真正的变量是「清理时机」**：流程会在超时后的某个时刻**「补画一次」那 24 段高亮**。
   - **清早了**（在它补画之前）⇒ 清完它再画 ⇒ **白清**
     （实测：跑批收尾清场清了 3 段，复查仍 24 段 —— 就是这个原因）
   - **清晚了**（在它补画之后，实测 **400ms 即够**）⇒ 一次清干净

   **实现（不阻塞主流程）：在每件清理之后挂一个 600ms 的 setTimeout 再清一次高亮**
   ```js
   // 在每件的清理块里、写 r.止 之前
   try {
     const __lh走3 = (n, d) => {
       if (d > 8 || !n || !n.children) return;
       for (const cc of Array.from(n.children)) {
         try { if (((cc.constructor || {}).name || "").indexOf("GridHighlight") > -1 && cc.clear) { cc.clear(); if (r) r.延迟补清 = 1; } } catch (e) {}
         __lh走3(cc, d + 1);
       }
     };
     setTimeout(() => { try { __lh走3(canvas.stage, 0); } catch (e) {} }, 600);
   } catch (e) {}
   ```

   **实测验收（三件，含 12 秒超时的噬烟流→火墙术）：**
   ```
   每件记录：龙之息(锥) 完成211ms 清高亮2 延迟补清1
             月华之光   完成449ms 清高亮2 延迟补清1
             噬烟流     超时12000ms 清高亮3 延迟补清1
   清场：清目标·清模板文档·清模板预览·清Sequencer·清网格高亮x3·清召唤物·
         清Region·清施法者效果·清画布裸图形·清测距器·清workflow·还原场景工具
   终态：高亮 0 · Region 0 · 模板 0 · midi框 0 · 应用26 · 工具 tokens   ⇒ ★ 全项通过
   ```

   **⇒ 结论：不需要跳过任何带模板的件。全量照跑，跑完不留痕。**
3. **找到 dnd5e 层那个「等模板」的 Promise 并取消** ——
   `MidiQOL.Workflow.clearWorkflows()` 只能清 midi 层（实测清成功但 `use()` 仍不 resolve），
   **悬挂在 dnd5e 层**。要取消得读 dnd5e 源码找 `canvas.templates` 的放置流程 API —— **未验证，禁止猜。**

## 7. 受控实验怎么做（验证清理逻辑有效性的唯一正确姿势）

**错误做法**：把测试对象造在跑批**之前** ⇒ 它会被跑前快照收录 ⇒ 按设计不删 ⇒ **得不出结论**。（第一次就这么干的）

**正确做法**：
1. 点火跑批（**不要 await**，长任务在后台跑）
2. **跑批运行期间**（如 1.5 秒后）手动造测试对象：
   - 造一个 Region（`canvas.scene.regions.create(...)`）
   - 造一个裸图形（`new PIXI.Graphics().drawCircle(...)` 挂到 `canvas.stage`）
   - 造一片高亮
3. 跑完看结果里的**清场记录**，逐条核对是否出现对应的清理条目
4. **同时复查**：跑批之前就有的对象**一个都没被删**（反证安全）

**实测结果示例**：
```
清场: 清Region:LH期间测试区 ✓ | 第 1 件 清裸图形 1 ✓ | 清网格高亮x3 ✓
复查: Region 0 / stage 只剩 3 标准组 / 非组残留 [] / 施法者效果 8→8（一个没误删）
```

## 8. 跑批自身的操作纪律（每条都有实测代价）

1. **长任务必须「点火不 await + 结果写全局变量」**
   实测：relay 对单次 `foundry_execute_js` 有请求超时（35 秒即 HTTP 408）。
   **犯了两次「只 return 不写全局变量」的错，超时即丢**（v16 的 901 件名单就是这么丢的，后来挖不回来）。

2. **每版必须换版本号**，否则无法定位用户装的到底是哪一版。
   曾出现两版都叫 `LH.22`（102018 / 102055 字节），严重失误。

3. **relay 的 forbidden-patterns 是子串正则**（24 条），**注释里的也算**：
   - `game.settings.settings` 会命中 `game.settings.set` ⇒ 改用 `game["settings"]["settings"]`
   - 想用 `new Function(...)` 做语法自检 ⇒ 命中 `Function(` ⇒ 去掉
   - `Proxy` / `import(` 是子串匹配 ⇒ 任何含这两个词的地方都会中招

4. **对象字面量的键不能含 `/`**（`含攻/豁/伤活动` ⇒ `/` 被当除法 ⇒ `Unexpected token '/'`）

5. **深层嵌套括号易错**（`missing ) after argument list`）⇒ 用 for 循环 + push，别硬写嵌套箭头函数。

6. **改世界内宏用「读取 → 定点替换 → 写回」，别重传整个宏**
   - 先 `const c = String(宏.command)`，再 `c.split(旧).length - 1` **确认命中数**，
   - **命中数 ≠ 1 就别改**（0 = 锚点不对，>1 = 会误改）
   - 换行用 `String.fromCharCode(10)` 拼接，**避免转义层级歧义**（我在这上面栽过一次）

7. **改完必须用真实跑批验证**，不能只做静态检查。
   实例：v25 五处替换全部「命中并写入」，但**跑起来才发现选择器多了一个引号**，
   导致看门狗对所有框失明。**如果只改不验，这个 bug 会跟着跑完全库 2684 件。**

8. **每调一次 `foundry_execute_js`，世界聊天多一条 `⚠ REST API execute-js:` 记录**（实测累计 373+ 条）。
   `use(..., {create:true})` 每件必产一张聊天卡 ⇒ 跑批要顺手清窗口内新增的聊天。

9. **别把结果判据放在名字或类型上**：
   - `pack.getIndex()` 的条目字段是 **`_id` 不是 `id`**（`getDocuments()` 才是 `id`）
   - `frame.instanceof Map` 这类判断要实测（`foundry.applications.instances` 实测是真 Map，`set`/`delete` 可安全覆写）
