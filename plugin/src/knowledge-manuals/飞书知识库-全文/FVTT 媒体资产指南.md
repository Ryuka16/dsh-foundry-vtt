# FVTT 媒体资产指南

## **概述**

本文将引导你了解在 Foundry VTT 中使用媒体资产的最佳实践和文件格式注意事项，包括命名、组织和格式化资产的相关信息。

## **文件结构与命名**

本节详细介绍文件命名和组织的推荐方法。合理的组织、文件命名和格式设置将确保 Foundry 尽可能平稳运行，降低问题或文件丢失的风险，并可能提高你自身的工作流程效率。

### **文件夹结构**

建议你根据不同资产的用途按主题组织文件夹：

- `/artwork` – 用于日志、物品或 handout 中包含的美术素材
- `/audio` – 用于音频文件
- `/tiles` – 用于场景中使用的图块图像
- `/tokens` – 用于角色的 Token 图像
- `/maps` – 用于场景中用作背景的地图

<callout emoji="❗">
自v13开始，fvtt将只允许你通过其自身的文件管理器向/assets文件夹中上传资产，/assets文件夹可以是:
- `.../Data/assets `： 用户数据路径下的资产文件夹
- `.../Data/worlds/[world-id]/assets`：特定世界内的资产文件夹
- `.../Data/modules/[module-id]/assets`：特定mod内的资产文件夹
</callout>

### **文件命名规范**

由于 Foundry VTT 是一个 Web 服务器，它遵循 Web 服务器所期望的文件命名规范，因此你的资产文件结构和文件名也应相应标准化。最常见的注意事项包括：

\- **文件名和文件夹中不要包含空格**  

  例如：应避免使用 `/my awesome content/maps/fortress of doom.jpeg`。应去掉空格，或用连字符（-）和下划线（\_）代替。因此，上述文件和文件夹应改为：`/maps/my-awesome-content/fortress_of_doom.jpeg`

\- **避免在文件名中包含不必要的元数据**  

  内容制作者常常在文件名中加入元数据，以便在存在多种变体时方便识别。

  例如：`fortress_of_doom(30x25-3000x2500-gridless).jpeg` 本身并非错误，但应简化为 `fortress_of_doom.jpeg`，因为额外信息并非必需。

\- **不要在文件名或文件夹中使用可能导致问题的特殊字符**  

  最好只使用普遍可读的字符，以避免破坏文件路径或在 Foundry VTT 读取文件名时产生错误。这包括空格（如上所述）、非英语键盘特有的字符，以及以下字符：`* . " / \ [ ] : ; | , & = + $ ? % #`

### **Token 通配符命名规范**

如果你要为同一基础 Token 提供多种变体，文件命名应使所有 Token 都以相同的前缀开头。通常应按“生物名称 – 主要变体 – 次要变体”的顺序命名。

示例：  

`red-guard.png, blue-guard.png, green-sword-guard.png, green-guard-spear.png`  

应改为：  

`guard-red.png, guard-blue.png, guard-green-sword.png, guard-green-spear.png`

这样，Foundry 的通配符 Token 路径就可以轻松使用 `guard-*.png` 来随机获取红色、蓝色或绿色的守卫，或使用 `guard-green-*.png` 来随机获取绿色守卫（剑或矛）。

## **美术资产**

为 Foundry 生成图像资产时，遵循一些最佳实践有助于优化你的内容以进行分发。

### **图像文件格式**

Foundry 支持以下图像文件格式：`.avif, .jpg, .jpeg, .png, .svg, .webp`。根据你是为 Token、图块还是场景地图创建素材，推荐格式略有不同。

#### **图像格式详解**

\- **WebP**  

  目前 Foundry VTT 中表现最佳的图像格式是 WebP，它在同等质量下比 JPEG 拥有更小的文件大小，且支持透明度，实现了最佳的质量/尺寸比。

  WebP 使用更复杂的压缩算法，需要客户端 CPU 做更多工作。通常这种权衡是值得的，因为可以减少网络传输，更多地利用客户端 PC 的性能。同样的道理也适用于音频编解码器（如 OGG）。

\- **SVG**  

  对于不需要很高视觉复杂度的图像，可以使用 SVG。它拥有极小的文件大小，支持透明度，可轻松制作动画，且可缩放至任意尺寸而不会明显损失质量。如果你正在制作图块、Token 或图标，且需要透明度和缩放能力，但不需要极其复杂的色深和细节，可以考虑使用 SVG。  

<callout emoji="❗">
  **📌 提示**：要在 WebGL 画布上使用 SVG 图像，SVG 文档必须在标记中显式指定默认宽度和高度，例如：  
> `<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 512 512" width="512" height="512">`
</callout>

\- **PNG**  

  作为一种无损压缩格式，PNG 的文件大小通常比其他格式大得多。建议将 PNG 用于较小尺寸的图像（带或不带透明度），这样文件大小仍可接受。对于非常大的图像（如场景背景）使用 PNG 会导致文件过大，增加玩家接收和加载的时间。

\- **JPEG 或 JPG**  

  JPEG 文件非常适合大尺寸图像，因为它们通常具有较小的文件大小，但代价是采用高压缩率的有损压缩方法，会产生视觉伪影，使图像显得颗粒感较重。JPEG 最适用于中等尺寸、不需要极高保真度或不会被玩家长时间注视的图像。在文件大小方面，使用 JPEG 作为场景背景通常比 PNG 更好，但压缩会严重影响图像清晰度。

### **Token 资产**

在设计用于 Foundry 的 Token 素材时，最好考虑尺寸、质量和图像方向。除非制作肖像风格或“Pog”风格 Token，否则俯视 Token 应以支持透明度的格式（webp 或 png）提供，像素尺寸应为正方形，且面向正南。具体原因详述如下。

#### **Token 尺寸与方向**

**尺寸**  

用于 Foundry 的 Token 分辨率，对于中型或大型生物通常在 200px 至 400px 见方。400x400(px) 已逐渐成为 Token 制作的行业标准。当放大 Token 时，我们希望获得比战棋地图本身更高的细节分辨率。Foundry 支持最大 3 倍放大，因此如果 Token 分辨率达到战棋地图网格尺寸的 3 倍，放大后仍能保持可见的质量。

**方向**  

Foundry VTT 默认 Token 美术的自然朝向是“向南”。如果你的原始图像中的 Token 并非朝南，建议将 Token 图像旋转为朝南。或者，用户可以在 Token 配置中使用 **垂直翻转** 复选框，将朝北的 Token 翻转为朝南。

请避免制作朝向对角线的 Token（例如朝东南或朝西南），因为在 Foundry 应用中没有办法修正这种初始方向，当这些 Token 与旋转功能结合时，看起来会很不自然。

### **场景/地图资产**

Foundry 对希望打包分发地图内容的制作者非常友好。以下是为 Foundry VTT 制作地图时需要考虑的重要准则：

#### **场景背景指导**

\- **仔细对齐地图的网格**  

  Foundry 假定网格从图像的左上角开始。网格应完全与图像边缘对齐，不得有间隙或超出。最简单的方法是确保地图描绘的是整数个网格单元，没有部分方格。例如，一个 20×20 个方格、网格尺寸为 100px 的场景，其地图图像应为 2000×2000(px)。请注意，Foundry 假定网格从图像左上角开始，因此在布置地图素材时请将此因素考虑在内。

\- **从最终地图图像中排除可见网格**  

  虽然地图图像必须与网格对齐，但最好不要在图像本身中包含预渲染的网格。这样用户就可以在 Foundry 中更好地自定义地图——应用不同的网格类型、用于无网格游戏、更改网格颜色或进行其他 VTT 能够提供的调整。

### **视频和动画资产**

Foundry VTT 支持三种关键视频文件类型：`.webm`、`.mp4` 和 `.m4v`。

对于透明视频素材（例如动画图块或 Token），`.webm` 通常能提供最佳体验，因为它画质高且文件体积小。对于动画素材（地图、图块和背景），推荐使用 `.webm`、`.mp4` 和 `.m4v`。

#### **质量与比特率考虑**

虽然 Foundry 不限制场景可以使用的文件大小，但请务必记住，场景必须分发给所有连接的玩家（以及潜在的 GM）。作为指导，Foundry 建议尽量将视频地图文件大小控制在 50MB 左右或更小，以便于顺利分发。不过，Foundry 用户可以通过集成 S3 支持、使用预加载功能，或者主机和客户端都具有足够的数据传输速率来缓解较大文件大小的问题。

总体而言，对于非透明的场景地图以及透明的图块或 Token，推荐使用 webm。mp4、m4v 和 webm 之间的文件大小差异明显，且不会显著降低质量。

视频文件理想情况下应以大约 30fps 或更低的速度渲染。  

如果你的视频包含音频，可以将音频作为单独文件提供，由 Foundry 的音频框架触发，以减少文件大小的影响。更多关于音频资产的信息，请参见下文相关部分。

**视频编解码器和比特率**  

Foundry 推荐使用针对在线流媒体优化的编解码器和比特率。以 h264 编码的可变比特率（VBR）文件通常性能最佳且保持高质量。如果你打算使用约束或固定比特率渲染视频，可考虑使用 libx264 等编解码器进行双通道编码，比特率设为 2–5 Mb/s。质量百分比应保持在 60–80%，以减少视觉伪影。

## **音频资产**

#### **比特率考虑**

尤其是在流式传输音频时，文件的比特率通常是决定 Foundry 中播放平滑度和音质的最重要因素。

较高的比特率提供更高质量的采样，但文件更大，可能无法在需要播放时及时流式传输完毕；而较低的比特率则更容易通过互联网连接流式传输，但可能听起来明显压缩过，或者整体质量较低。

**总的来说，128kbps 是建议在 Foundry 中使用的最低音频质量，192kbps 是建议的最高值。** 128kbps 在音质和较小文件大小之间提供了最佳平衡。使用高于 192kbps 的比特率对大多数玩家来说不会带来明显的音质提升。

#### **音频格式**

Foundry 目前支持 OGG、MP3、FLAC、WAV、WEBM 和 OPUS 格式的音频播放。音频格式的选择也是一个重要考虑因素，因为压缩方式会对音质产生不同程度的影响。混响、钹声、其他鼓采样、某些垫音或清脆的乐器声往往最容易受到音频压缩的影响，因此不同素材的效果可能不同。某些编解码器在导出特定声音、人声甚至音乐类型时表现更佳。你对格式和编解码器的选择也可能受限于你使用的工具或数字音频工作站（DAW）。

以下是 Foundry 支持的音频格式及其各自的优缺点概览。

##### **音频格式详解**

\- **OGG**  

  整体上最适合在线流式传输的音频格式。一般的 OGG 文件与 128kbps 的 MP3 文件大小相近，但音质更清晰。此外，OGG 还附带一个优点——在支持完美循环的音频播放器中可以干净地循环播放。许多工具和 DAW 也能原生导出为 OGG 格式，使其易于创建。不过，Safari 不完全支持 OGG 文件。

\- **MP3**  

  在音质和文件大小之间提供了相当不错的平衡，但压缩效率不如 OGG，且无法干净循环。几乎任何能够播放声音文件的设备都能播放 MP3。诸如 LAME 之类的 MP3 编码器有时在转换文件中可能出现伪影或量化误差，但总体来说仍是一个安全的选择。

\- **FLAC**  

  一种无损音频格式，文件大小尚可接受。FLAC 文件可干净循环，且不会出现压缩带来的音质下降。但 FLAC 的比特率通常比标准 mp3 文件大。FLAC 仍然有用，特别是对于容易在压缩中受损的采样，或者在带宽不成问题的环境（例如通过局域网托管的服务器）中。

\- **WEBM**  

  一种为 Web 设计的有损音频格式，品质尚可。像 Vorbis 这样的 WEBM 编解码器与 MP3 一样采用有损压缩，但文件往往更小，质量损失更少。不过，某些浏览器（如 Safari）不原生支持 WEBM，而且大多数 DAW 无法导出纯音频的 WEBM 文件。

\- **WAV**  

  WAV 文件在在线流式传输中往往不是好选择——未压缩的 WAV 能以完好的清晰品质播放，但文件大小可能比压缩格式大一个数量级。对于大多数听众来说，这一缺点几乎总是超过音质上几乎无法察觉的差异。

\- **OPUS**  

  Opus 是一种有损音频编码格式，专为在低带宽和低比特率下工作而设计，同时不会牺牲太多质量。在相似的压缩水平和较高的比特率下，它通常比其他有损格式（mp3、webm）具有更高的质量。

#### **转换音频**

音频程序（如 Audacity）可免费在线获取，允许在多种编解码器下导出各种格式的音频。上述 Audacity 支持导出为 WAV 和 OGG，并可通过免费插件添加对 MP3、FLAC 和其他格式的导出支持。

<callout emoji="❗">
**📌 提示**：将文件从一种“有损”格式（如 MP3 或 OGG）转换为另一种，只会重新压缩一个已经压缩过的声音文件，并可能降低音质。此外，将有损文件转换为未压缩的 WAV 格式并**不会**恢复损失的音质！最好的做法是拥有一个无损源文件（如 WAV 或 FLAC 音轨），然后**一次性**将其转换为你希望 Foundry 使用的目标格式。
</callout>
