# FVTT 提问指南：如何高效定位问题与提问

在 Foundry VTT（以下简称 FVTT）的使用过程中，由于其高度可定制性（包含各种系统 System、模组 Module、宏 Macro 以及不同的主机托管方式），遇到技术问题是难以避免的。

提出问题不代表群友就有义务帮你进行解答，所以提出问题之前请确保自身已经进行足够的问题处理，仍然无法解决。当你提出问题并且真正提供了相应的环境、日志、截图等足够帮助大家辨识你的故障的问题的时候，群友基本都是友善的。

## 提问前的自我排查

在向社区或开发者发问之前，请尝试以下基础排查步骤。这不仅能节省他人的时间，通常也能帮你直接找到原因：

- **确认影响范围：**  
大部分 FVTT 的异常是由模组（Module）冲突、模组与系统不兼容或模组未适配 FVTT 核心（Core）版本引起的。

  - 建议在管理页面中，尝试以**安全模式（Safe Mode）**启动世界，或者手动禁用所有非必要模组，观察问题是否依然存在。
  - 如果禁用后问题消失，可以使用类似 *Find the Culprit!* 的排查工具，逐步启用模组以锁定引起冲突的具体模组。
  - 如果是多模组系统问题，请先排查到尽量小的范围。
- **检查更新：**  
确认你的 FVTT 核心版本、游戏系统（System）以及相关模组是否处于兼容范围内。
- **搜索已知问题：**  
在 FVTT 官方 Discord 频道、相关模组的 GitHub Issues 页面，或者相关的社区论坛中又或者本篇教程的<cite doc-id="Z9gJwtpNQihiCXkPRkscJJIZnMd" file-type="wiki" title="常见问题" type="doc"></cite>，搜索关键词以确认是否已有类似的报告和解决方案。

## 如何清晰地描述问题

当排查无果需要提问时，请尽量保证信息精准，避免含糊不清的表述。

- **描述目标，而不是猜测：**  
说明你原本想要实现什么效果，以及实际呈现了什么状态。不要只贴出你猜测的“原因”，这可能会引导解答者走向错误的方向。

  1. “我制作了关于XX特性的条目，其中包含了伤害判定，DAE效果”
  2. “DAE效果包含让目标的AC降低2”
  3. “希望点击目标应用的时候进行豁免，若豁免失败应用伤害和效果”
- **按时间或操作顺序描述步骤：**  
清晰列出导致问题发生的每一步操作。例如：

  1. “我创建了一个新的 Actor（角色标签）。”
  2. “双击打开其角色卡，制作了‘特性’。”
  3. “用T选择了一个地方单位，然后点击这个特性”
  4. “聊天框内弹出了窗口，伤害已经应用但是DAE效果并没有生效”
- **避免无意义的词语：**  
标题或内容中写“救命”、“急”、“在线等”通常不会加速问题的解决，提供详实的数据才会。
- **耐心的等待：**漫无边际的提问是近乎无休无止的时间黑洞。最有可能给你有用答案的人通常也正是最忙的人（他们忙是因为要亲自完成大部分的处理工作）。这样的人对无节制的时间黑洞相当厌恶，所以他们也倾向于厌恶那些漫无边际的提问。

## 收集并提供关键环境信息

FVTT 的运行依赖于多个层级的软件协作。提问时，请务必主动提供以下“环境上下文”：

- **FVTT 核心版本（核心版本）：** 例如，`版本 11 Build 315` 或`版本 12.324`。
- **游戏系统（Game System）及其版本：** 例如 `DnD5e v3.1.2` 或 `Pf2e v5.13.5`。
- **服务器托管方式（Hosting）：**

  - 本地运行（Node.js / 官方客户端）
  - 第三方托管服务（如 The Forge, Molten Hosting）
  - 自行搭建服务器（如 腾讯云/阿里云/Oracle Cloud，是否使用了 Docker，是否配置了 Nginx 反向代理等）
- **客户端浏览器信息：** 例如 `Chrome`、`Firefox` 或 FLC 等。
- **模组状态：** 对应的模组版本号，比如 Midi-qol 13.0.63

## 如何获取和提供日志与截图

对于技术性问题，口头描述往往不如一行错误日志直观。以下是收集 FVTT 核心信息的具体方法：

### A. 浏览器控制台日志（Console Logs）—— 最重要

大部分前端渲染、模组报错、宏运行失败都会记录在浏览器的控制台。

1. **打开控制台：**

   - 在 Chrome / Firefox / Edge 浏览器中，按下键盘上的 `F12`（Mac 上为 `Cmd + Option + I`），然后切换到 **Console（控制台）** 标签页。
   - 如果使用 FVTT 官方桌面客户端，同样可以按下 `F12` 打开此界面。
2. **重现问题：** Keep 控制台打开，然后在 FVTT 中重新进行刚才报错的操作。
3. **定位红字：** 寻找控制台里出现的**红色错误信息（Error）**。
4. **导出或截图：**

   - 可以直接截取红字部分的屏幕截图（确保能看清报错的堆栈信息 Traceback）。
   - 也可以在控制台空白处右键，选择“Save as...（另存为）”保存为文本日志发送。

### B. 服务器日志（Server Logs）

如果是连接失败、文件上传异常、启动崩溃或无法加载世界，通常需要查看服务器端日志：

- **本地/自建 Node.js 运行：** 查看启动 Node.js 进程的终端（Terminal）输出，或者查看 FVTT 数据目录（User Data）下 `Logs` 文件夹中的 `error.log`。

### C. 结构化的截图与视频

- **不要用手机拍摄屏幕：** 手机拍照往往难以辨认代码和文字。请使用系统自带的截图工具（如 Windows 键 + Shift + S）截取清晰的图片。
- **必要时录制动图/视频：** 如果交互过程比较复杂，可以使用轻量级录屏软件录制一段几秒钟的操作过程，以便他人复现。

## 关于如何看待问题回复

### RTFM和STFW：你基本上搞砸了

有一个古老而神圣的传统：如果你收到RTFM （Read The F\*\*king Manual）的回应，回答者认为你应该去读那的手册。基本上他是对的，你应该去读一读。

RTFM 有一个年轻的亲戚。如果你收到STFW（Search The F\*\*king Web）和ATFA（ASK The F\*\*king Ai）的回应，回答者认为你应该到的网路上搜寻过了。那人多半也是对的，去搜寻一下吧。 

通常，用这两句之一回答你的人会给你一份包含你需要内容的手册、一个网址或者一个能找到资料的地方，而且他们打这些字的时候也正在读着。这些答覆意味着回答者认为：

**你需要的资讯非常容易获得，你自己去搜寻这些资讯比灌给你能让你学到更多。**

你不应该因此不爽；因为依照标准，他已经表示了对你一定程度的关注，而没有对你的要求视而不见。你应该对他感谢。

### 如果还是搞不懂

如果你看不懂回应，别立刻要求对方解释。像你以前试着自己解决问题时那样（利用手册，FAQ，网路，身边的高手），先试着去搞懂他的回应。如果你真的需要对方解释，记得表现出你已经从中学到了点什么。

比方说，如果回答：**“我已经把这个模组更新到DND5e所需要对应的版本，也安装了XX模组，但是启动的时候仍然提示缺少依赖”**。你是指这里面的其他模组？还是我看漏了什么？

### 处理无礼的回应

很多群友中看似无礼的行为并不是存心冒犯。相反，它是直接了当，一针见血式的交流风格，这种风格更注重解决问题，而不是使人感觉舒服而却模模糊糊。

如果你觉得被冒犯了，试着平静地反应。如果有人真的做了出格的事，群组或论坛中的前辈多半会招呼他。如果这没有发生而你却发火了，那么你发火对象的言语可能在社群中看起来是正常的，而你将被视为有错的一方，这将伤害到你获取讯息或帮助的机会。

另一方面，你偶而真的会碰到无礼和无聊的言行。与上述相反，对真正的冒犯者狠狠地打击，用犀利的语言将其驳得体无完肤都是可以接受的。然而，在行事之前一定要非常非常的有根据。纠正无礼的言论与开始一场毫无意义的口水战仅一线之隔，自己莽撞地越线的情况并不鲜见。如果你是新手或外人，避开这种莽撞的机会并不高。如果你想得到的是讯息而不是消磨时光，这时最好不要把手放在键盘上以免冒险。

## 如何更好地回答问题

**态度和善一点。**问题带来的压力常使人显得无礼或愚蠢，其实并不是这样。

**对初犯者宽容一些。**对那些坦诚犯错之人没有必要当众羞辱，一个真正的新手也许连怎么搜寻或在哪找常见问题都不知道。

**如果你不确定，一定要说出来！**一个听起来权威的错误回覆比没有还要糟，别因为听起来像个专家很好玩，就给别人乱指路。要谦虚和诚实，给提问者与同行都树个好榜样。

**如果帮不了忙，也别妨碍他。**不要在实际步骤上开玩笑，那样也许会毁了使用者的配置 --有些可怜的呆瓜会把它当成真的指令。

**试探性的反问以引出更多的细节。**如果你做得好，提问者可以学到点东西 --你也可以。试试将蠢问题转变成好问题，别忘了我们都曾是新手。

**尽管对那些懒虫抱怨一声 RTFM 是正当的**，能指出文件的位置（即使只是建议个 Google 搜寻关键词）会更好。

**如果你决定回答，就请给出好的答案。**当别人正在用错误的工具或方法时别建议笨拙的权宜之计，应推荐更好的工具，重新界定问题。
