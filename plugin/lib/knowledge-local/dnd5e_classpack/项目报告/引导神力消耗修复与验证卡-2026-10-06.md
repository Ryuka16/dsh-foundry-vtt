## 二 · 根因（源码级，实测坐实）

### 坏数据长这样

三件的 `consumption.targets` 都写死了 **compendium 的 uuid**：

```json
[{"type":"itemUses","value":"1",
  "target":"Compendium.dnd5e_classpack.class-abilityphb.Item.v8z4Z2NuBAbYnjxk",
  "scaling":{}}]
```

### dnd5e 的真实解析机制（`dnd5e.mjs`，`Activity#_remapConsumptionTarget`）

```js
/**
 * Remap a UUID or identifier in a consumption target to the ID of an item on the actor.
 */
_remapConsumptionTarget(target) {
  if ( !target || !this.actor || this.actor.items.has(target) ) return target;

  // Re-link UUID target
  const { type } = foundry.utils.parseUuid(target) ?? {};
  if ( type === "Item" ) {
    const item = this.actor.sourcedItems?.get(target)?.first();   // 按「来源 uuid」找
    if ( item ) return item.id;
  }
  // Re-link identifier target
  else {
    const item = this.actor.identifiedItems?.get(target)?.first(); // 按 identifier 找
    if ( item ) return item.id;
  }
  return target;   // ← 找不到就原样返回 ⇒ 后续 actor.items.has() 失败 ⇒ 报警告
}
```

配套（同一文件）：

```js
static async consumeItemUses(config, updates) {
  const item = this.target ? this.actor.items.get(this.target) : this.item;
  if ( !item ) throw new ConsumptionError(game.i18n.format("DND5E.CONSUMPTION.Warning.MissingItem", {...}));
  ...
}
// 准备阶段：
//   target.target = this._remapConsumptionTarget(target.target);
//   if ( !actor.items.has(target.target) ) actor._preparationWarnings.push({ message, ... });
```

**⇒ 三种写法都合法：① 空串（指向自己物品的 uses）② 物品 uuid ③ identifier。**
**⇒ 判据只有一条：能不能在**这张 actor**上找到。**

### 为什么偏偏是「引导神力」坏

包里有**两个**同名同 identifier 的引导神力：

| 物品 | 包内 id | identifier | uses.max |
|---|---|---|---|
| 引导神力 Channel Divinity | `v8z4Z2NuBAbYnjxk` | `channel-divinity` | `1` |
| 引导神力 (牧师) | `WPevnsjK8Cjd9Fcl` | `channel-divinity` | `floor((@classes.cleric.levels+6)/12)+1` |

牧师卡 advancement 装的是**后者**（带等级公式那件），而三件的 target 写死指向**前者** ⇒ `sourcedItems` 按 uuid 查找 ⇒ 对不上 ⇒ 原样返回 uuid ⇒ 报「找不到耗用项」。

**⇒ 写 identifier（`channel-divinity`）时，两个版本都能命中 ⇒ 这就是这个包设计的正确写法（实测确认）。**

## 五 · ★ 老验收卡为什么改不动（重要坑）

### 现象

```js

await it.update({ "system.activities": acts });    // ✗ Cannot read properties of undefined (reading 'id')

await it.delete();                                 // ✗ Item "HhyVN6IIStU6CwAc" does not exist!
await actor.deleteEmbeddedDocuments("Item", [id]); // ✗ 同上
// relay 工具 foundry_delete_entity(Actor.<id>.Item.<id>)  // ✗ 同上
```

**矛盾点**：`actor.items.get(id)` 说有、`actor.toObject().items` 里也有（139/139 唯一 id、无重复），但 update/delete 都报「不存在」。

### 结论（未深挖到根因，但有可用判据）

- **这批 389 张验收卡是「世界内连续批量 API 创建」出来的 ⇒ 内存集合与文档层不一致。**
- **两条删除路径（脚本内 + relay 工具）都失败 ⇒ 不是权限、不是 relay 的问题。**
- **⇒ 这批卡上的物品改不动、删不掉；只能整卡废弃或让用户重新拖。**

**老验收卡上的旧副本一律不修 —— 让用户从包重新拖（包已修，拖出来就是对的）。**

## 八 · 可复用判据（下次直接用）

1. **扫「消耗目标是否命中」的脚本模板**（对任意 actor 的任意物品）：
```js
function 命中(a, i) {
  const acts = i.toObject().system.activities || {};
  const 坏 = [];
  for (const k of Object.keys(acts)) for (const t of (acts[k].consumption && acts[k].consumption.targets) || []) {
    const tv = String(t.target || "");
    if (!tv) continue;                                   // 空串 = 指向自身，正常
    let ok = a.items.has(tv);
    if (!ok) {
      const pu = foundry.utils.parseUuid(tv) || {};
      const it = pu.type === "Item" ? a.sourcedItems.get(tv) : a.identifiedItems.get(tv);
      ok = !!(it && it.size);
    }
    if (!ok) 坏.push(String(i.name).slice(0,22) + " → " + tv.slice(-34));
  }
  return 坏;
}
```

2. **dnd5e 报「找不到耗用项」时，永远先问两件事**：
   - 卡上到底有没有那个池？（没有 ⇒ 正常报错，不是包的错）
   - 有池的话，**写的是 uuid 还是 identifier**？（uuid ⇒ 必须与卡上那件的来源 uuid 完全一致；identifier ⇒ 只要撞上 identifier 就行）

3. **包内写法优先级：identifier > uuid > 空串**。identifier 对「同名多版本」的池（引导神力就有两个）才稳。

4. **批量建卡（几百张连建）会产生改不动、删不掉的僵尸物品** ⇒ 验收卡这类中间产物要少量建、立即读回验证。
