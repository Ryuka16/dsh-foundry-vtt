# dnd5e_classpack · 验收卡结构性验收报告（2026-10-06 晚）

## 一 · 起因

用户建完 390 张 L20 验收卡后，**人工点开第一张就发现**：

> 「OK了，但是没有木桩，我的PL也会在车卡，你自己搞吧，不要动我PL的卡属性数据，不要把服务器搞的太卡」
> （随后）「高等术法会大法师 Mage of High Sorcery 什么也没有」

⇒ 这是**人工验收发现的第 1 个问题**，也是验收方法有效的第一个证明。

## 二 · 根因与修复

### 2.1 根因（包内数据损坏）

`dnd5e_classpack.BackgroundList` 包里 **2 件背景**的 `system.advancement` 是空壳：

```
索兰尼亚骑士 Knight of Solamnia      (FYFPB20vvtDQUcYR)  advancement = {"0lxdyaAkHGKVQ0qR":{"level":0}}   ← 无 type 无 _id
高等术法会大法师 Mage of High Sorcery (f1YSso6o1t0l4xoI)  advancement = {"XpEwN2cYZPreHCFv":{"level":0}}
```

**`type` 为 undefined ⇒ dnd5e 不认识这个 advancement 类型 ⇒ 静默不授予任何东西。**

**全库扫描**（5 包 479 件 / 395 件有 advancement / advancement 总数 2439）：
| 包 | 件数 | 有 advancement |
|---|---|---|
| classes-new | 14 | 14 |
| subclass | 122 | 122 |
| races-item | 170 | 170 |
| BackgroundList | 85 | **85（其中 2 件坏）** |
| BackgroundFeature | 88 | 4 |

⇒ **坏件 = 2 件，全在 BackgroundList，全部是龙枪（Dragonlance）背景。不是成批问题。**

### 2.3 修复（已写入包，读回验证）

按**包内正常背景**（拉铎斯邪教徒，5 个 advancement）的同构结构补：

```js
// ItemGrant 结构（configuration 键 = items / optional / spell）
{ _id: rid, type:"ItemGrant", configuration:{ items:[{uuid, optional:false},...], optional:[], spell:null },
  value:{}, level:0, title:"", hint:"", icon:null, flags:{}, classRestriction:"" }
// 特性那个 ItemGrant 的 title = "获得背景特性"
// Trait 技能（grants 固定给）
{ _id: rid, type:"Trait", configuration:{ mode:"default", allowReplacements:true, grants:["skills:ath","skills:sur"], choices:[] },
  value:{ chosen:[] }, level:0, title:"", hint:"", icon:null, flags:{} }
// Trait 语言（包内 40 个背景在用的标准写法）
{ _id: rid, type:"Trait", configuration:{ mode:"default", allowReplacements:false, grants:[], choices:[{count:2, pool:["languages:standard:*","languages:exotic:*"]}] },
  value:{ chosen:[] }, level:0, title:"", hint:"", icon:null, flags:{} }
```

### 2.4 ★ 关键陷阱：dnd5e 的 advancement 是 ObjectField，update 是**合并不是替换**

```js
await d.update({ "system.advancement": 新对象 });   // ✗ 4 个新的加进去了，旧的坏键还在 ⇒ 变成 5 个
await d.update({ "system.advancement.-=旧键": null }); // ✓ 必须显式删旧键 ⇒ 变回 4 个
```
**实测**：第一次写入后读回 = 5 个（4 正常 + 1 个 `undefined@0`），补删旧键后 = 4 个全正常。

**旧值已冻结备份**：两件都从 `{"level":0}` 改成完整 4 项，回滚只需把 `system.advancement` 换回 `{"任意键":{"level":0}}`。

### 2.5 ★ 第二个陷阱：拖入 background 时 dnd5e **不自动跑** advancement

```js
// 从 compendium 拖背景到卡上 ⇒ item 建好了，但 advancement 一件都没授予
// 必须手动跑：
for (const adv of 背.system.advancement.contents) {       // ★ 是 Collection，用 .contents
  if (adv.type === "ItemGrant") await adv.apply(0, {}, { initial: true });
  if (adv.type === "Trait") {
    const au = await adv.automaticApplicationValue(0, { initial: true });
    if (au) await adv.apply(0, au, { initial: true });
  }
}
```
**实测（修复后重跑）**：
```
高等术法会大法师：ItemGrant ✓ / ItemGrant ✓ / Trait自动值 {"chosen":["skills:arc","skills:his"]} ✓ / Trait语言 chosen:[]（需玩家选）
  ⇒ 卡 9 件 → 14 件：+墨水 +墨水笔 +普通服装 +小包 +【高等术法入门】；技能 arc/his 已赋值
索兰尼亚骑士：  同上
  ⇒ 卡 9 件 → 14 件：+军衔徽记 +赌具(纸牌) +普通服装 +小包 +【索兰尼亚扈从】；技能 ath/sur 已赋值
```
**语言为空是正常的** —— 「任选两门」是选择型 advancement，`chosen:[]` 等玩家选。

## 四 · 结论与边界（诚实说明）

**✅ 已验的**：卡上「该有的东西有没有」—— 390 张全过，包内 2 件坏数据已修。

**❌ 未验的**：卡上那些东西「内容对不对」——
- 活动/效果的内部结构是否完整
- 中文描述 ⇄ 自动化实现是否一致
- 实际用起来能不能跑通、会不会报错

**⇒ 结构性验收 ≠ 效果验收。用户发现的这个恰好是结构性的，所以一眼可见；效果层的问题需要跑批或逐件比对方能暴露。**

## 五 · 方法学沉淀（本轮新增）

1. **「用户肉眼发现 1 个 → 我全库扫同类 → 一次修完」是效率最高的模式** —— 已验两次（震慑拳空壳 → 全库 2 件；本次背景空壳 → 全库 2 件）。
2. **扫 advancement 必须用 `d.toObject().system.advancement`** —— `d.system.advancement` 是 AdvancementCollection，`Object.keys()` 恒为 0（第一次扫描因此报「479 件全无 advancement」的假结果）。
3. **判据要有明确特征才能自动扫**：「`type` 是 undefined」是坏数据的硬特征，扫得出；「缺内容」没有特征，只能靠人眼或跑批。
4. **同包内找同构写法**：补数据前先扫包内正常件，照抄它们的 configuration 格式（本次语言写法从 40 个正常背景里抄到 `count:2 + pool:["languages:standard:*","languages:exotic:*"]`）。
5. **relay 脚本用纯 ASCII 变量名**：中文+`≤` 等符号组合触发过 `Invalid or unexpected token`。

### 7.4 ★ 三次实测：`optional` 两个值都不是「二选一」

| 配法 | 拖入（API `createEmbeddedDocuments`）结果 |
|---|---|
| `optional: false` ×2（原值） | 给 2 件 —— 两个都给 |
| `optional: true` ×2 | 给 **0** 件，且**不弹任何框**（`foundry.applications.instances` 无新增） |
| 换成 `ItemChoice`（原生「选 N 个」类型） | 给 **0** 件，也不弹框 |

**`ItemChoice` 的正确结构（dnd5e 规范化后的真实形状，实测读回）**：
```json
{"type":"ItemChoice","configuration":{
  "pool":[{"uuid":"..."},{"uuid":"..."}],        // 传字符串数组会被规范化成 {uuid}
  "choices":{"0":{"count":1,"replacement":false}}, // 传 {0:1} 会被规范化
  "type":"feat","allowDrops":true,"restriction":{"list":[]},"spell":null}}
```

### 7.5 ★ 两条路径行为不同（关键坑）

```js
// 路径 A：手动/宏调用 —— initial:true 会**覆盖** selected，全部给
await adv.apply(0, {}, { initial: true });                    // 给 2 件（忽略 optional）
await adv.apply(0, { selected: [一个uuid] }, { initial: true }); // 仍然给 2 件 ← initial 覆盖 selected
// 路径 B：dnd5e 自己的表单流程（真拖入走这条）—— 只应用非可选项
const selected = cfg.items.filter(i => !cfg.optional && !i.optional).map(i => i.uuid);
if ( selected.length ) await adv.apply(this.level, { selected });   // 源码：ItemGrantFlow._handleForm else 分支
```
**⇒ 结论：`initial: true` 下 optional 被忽略；只有不带 initial 的 selected 路径才尊重 optional。**
**⚠️ 因此「API 建 item 后手动 apply」**不能**用来验证真拖入行为 —— 必须让玩家真拖一次。**
