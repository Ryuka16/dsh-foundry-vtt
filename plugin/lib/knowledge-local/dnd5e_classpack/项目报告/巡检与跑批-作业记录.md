## 四 · 核心结论（已实测）

### 4.1 龙之息卡死的真因是 CPR，不是「需要玩家选」

| 条件 | midi 状态机轨迹 | 结局 |
|---|---|---|
| 带 CPR | 停在**第 1 步**（`stateTransitionCount=1`）：`WorkflowState_NoAction` → `WorkflowState_Suspend` | 12001ms 超时 |
| **摘掉 CPR**（唯一变量） | `WaitForDamageRoll`(7) → `DamageRollComplete`(11) → … → **`Completed`(17)** | **236ms 完成** |

源码依据：`WorkflowState_Suspend` 里 `error2(\`${this.workflowName} Workflow ${this.id} suspend should never be called\`)`；`processPlacedTemplates` 能置 `needTemplate=false`，但唤醒条件 `if (this.suspended && this.currentAction === this.WorkflowState_AwaitTemplate) this.unSuspend();` 永不成立 —— `performState` 循环每轮 `this.suspended = false`。
**⚠️ 不下「CPR 坏了」的结论** —— CPR 宏可能本就设计成要真人在场确认。

### 5.6 ★★ duration 的真相（Foundry 核心源码级，2026-10-06 实测）

**起因**：跑批实测发现「征服威压」「夺命之手(6级)」的效果显示为**永久**（描述说 1 分钟）；全库扫描发现 **120 件** effect 的 duration 是 `type:"turns"` 但只填了 `rounds`。

**结论：120 件是好的，我的判断作废。** Foundry 核心 `ActiveEffect.prototype._prepareDuration` 原文：

```js
_prepareDuration() {
  const d = this.duration;
  if ( Number.isNumeric(d.seconds) ) { ... return { type:"seconds", ... }; }
  else if ( d.rounds || d.turns ) {          // ← 只看 rounds/turns 的值，根本不读 d.type
    const cbt = game.combat;
    if ( !cbt ) return { type:"turns", _combatTime: undefined };   // ← 无战斗直接返回
    ...
  }
  return { type:"none", duration:null, remaining:null, label:"None" };
}
```

**三条硬事实**：
1. **`duration.type` 是死字段** —— 核心从不读它 ⇒ `type:"turns"` 配 `rounds:1` **完全有效**
2. 决定行为的是 **`seconds` / `rounds` / `turns` 的值**，不是 type
3. **turns 型时长需要战斗才能倒计时** —— `game.combat` 为 null 时连 `remaining`/`label` 都不返回

**⇒ 跑批时没有战斗（`game.combat` 为 null）⇒ turns 型效果的时长在跑批实测里**必然显示不全**，这不是数据错，是环境缺战斗。**
**⇒ v23 改进方向：跑批前开一场垫底战斗（`game.combats`），让 turns/rounds 型时长也进入可观测状态。**

## 六 · AC = 0 的真根因（用户报的现场 bug）

玩家「维兰」（`Actor.mCIwm7aluKWfu83k`，提夫林术士 3 级，AC 显示 **0**）：

```

```

**根因链（实测）**：
1. 该卡的 `ac.calc` 派生值是 `flat`，而 `flat = null` ⇒ AC 算成 **0**
2. `ac.calc` 的 **schema 是 `StringField`，初始值 `"default"`**
3. 卡上物品「龙族体魄 Draconic Resilience」自带一个效果：
   `system.attributes.ac.calc ｜ mode 2 (ADD) ｜ value "draconic"`
4. **对字符串字段用 mode 2（加法）⇒ 无效** ⇒ calc 永远回落到 flat

**⇒ 意图对（有龙族体魄就该用 draconic 公式 = `13 + @abilities.dex.mod` ⇒ 该是 16），写法错（字符串字段不能用加法模式）。**

### 6.1 ★ 已修复并实测（2026-10-06，用户授权选项 2）

**改法**：把该效果的 `system.attributes.ac.calc` 从 `mode 2` 改成 **`mode 5`（OVERRIDE）**。

```

```

**该效果原本有两条 changes（实测原文）**：
```json
[{"key":"system.attributes.hp.bonuses.overall","value":"+@classes.sorcerer.levels","mode":2,"priority":20},
 {"key":"system.attributes.ac.calc","value":"draconic","mode":2,"priority":20}]
```
**修复后（两条都保留，只改第二条 mode）**：
```json
[{"key":"system.attributes.hp.bonuses.overall","value":"+@classes.sorcerer.levels","mode":2,"priority":20},
 {"key":"system.attributes.ac.calc","value":"draconic","mode":5,"priority":20}]
```

**⚠️ 过程中犯的错（已修正）**：第一次 `effect.update({changes:[...]})` 只写了 AC 那一条，**把 `hp.bonuses.overall` 冲掉了**（Foundry 的 ArrayField 是**整段替换**不是逐元素合并）。已写回两条并读回校验条数 = 2。

### 12.4 新增坑：`getIndex()` 用 `_id`，`getDocuments()` 用 `id`

查包内 uuid 时用 `pack.getIndex()`，索引条目的字段是 **`_id`**（另有 `name`/`uuid`/`system`…），**没有 `id`** ⇒ 写 `x.id` 得到 `undefined`。
宏里的队列构造用的是 `pack.getDocuments()` + `d.id` ⇒ **宏本身没这个问题**，是临时脚本写错了。
（同一脚本的 `filter/map` 链式写法还报过一次 `Unexpected number`，改成 for 循环就过 —— 与既有经验一致：**脚本越平铺越稳**。）
