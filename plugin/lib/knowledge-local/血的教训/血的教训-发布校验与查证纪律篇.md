# 血的教训 · 发布校验与查证纪律篇

> **起因**：v1.1.5 发布的插件包里漏了 93 个样本文件，别人下载后资料库残缺；
> 用户追问「为什么」，我三轮里给出了相反结论，把用户绕晕。
> 本文记录根因与硬性规范。

---

## 0. 一句话根本

> 打包时我**假设**内容都在，从没数过包里到底有几个文件。
> 被用户质疑时，我**先解释再查证**，而不是**先查证再开口**。
> 结果：用户被迫当了我的校验器，还被我绕了三轮。

## 1. 事件经过（可复现，数字都是实测）

| 项 | 磁盘上 | git 仓库里 | 下载的 zip 里 |
|---|---|---|---|
| v1.1.5（用户/朋友下载的那版） | 116 个样本 | 23 个 | **23 个** |
| v1.1.6 | 116 个 | 23 个 | **116 个** |
| v1.1.7 | 116 个 | **116 个** | 116 个 |

- 那 93 个样本文件**从一开始就在磁盘上**（v1.1.0 起陆续加的），只是**一直没提交进 git**。
- v1.1.5 打包时按 **git 跟踪列表** 打 → git 里只有 23 个 → 包里只有 23 个。**93 个被静默漏掉。**
- v1.1.6 改了打包方式（从磁盘抓）→ 116 个全进包。**修的是「包」。**
- v1.1.7 才把那 93 个提交进 git → **修的是「仓库」**，跟下载 zip 的人无关。
- 结论：下载 v1.1.5 的人，资料库缺 93 个样本 + 1 篇文档 + 1 个工具。

## 2. 两个病根

1. **打包不校验产物**——「应该都在」是假设不是事实。发版前从没统计过 zip 内文件数。
2. **先开口后查证 + 护短**——第一次凭假设下结论「他不用换」；被质疑后，先讲「版本号内容一样」、让对方去点按钮验证，而不是立刻把包下载下来自己数。三轮里给出相反结论，用户被绕晕后说「你玩我呢」。

## 3. 硬性规范（写进工作流，不许再犯）

1. **发布前必数产物**：打包后立刻统计 zip 内关键文件数（样本数 / 文档数 / lib 文件数），与磁盘对比，不一致**不发版**。
2. **「补进 git」≠「补进包」**：仓库层与分发层是两件独立的事，改动后必须**分别**验证，不许用一句「已更新」糊过去。
3. **被质疑第一动作是查，不是解释**：用户说「不对吧」时，先跑命令拿证据，再开口。任何解释性话语都必须排在证据之后。
4. **不把验证推给用户**：能自己下载、读取、数出来的，绝不让用户去问第三方、点按钮或试一下。
5. **同一件事不给相反结论**：新证据推翻旧结论时，直接说「我上一条错了，实测是 X」，不做找补式铺垫、不绕弯。

## 4. 发版前检查清单（逐条打勾）

- [ ] zip 内样本数 = 磁盘样本数？
- [ ] zip 内 knowledge-docs 篇数 = 磁盘篇数？
- [ ] src ↔ lib 同步（`scripts/check-sync.mjs` 通过）？
- [ ] package.json description 里的工具数 = 实际注册工具数？
- [ ] Release 资产名 / 版本号 / 说明与实际内容一致？
- [ ] 临时产物（_pack-*、dist/）没被误提交进 git？

## 5. 写给下一个接活的智能体

> 用户问「为什么」的时候，他要的是**你当场去查出来的事实**，不是你的推理。
> 你手里有下载、读取、计数、跑脚本的全部能力——凡是能自己查的，一个字都不许推给他。
> 「我以为」这三个字，在用户面前等于「我没查」。
