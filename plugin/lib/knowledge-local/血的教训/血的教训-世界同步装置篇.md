## 0. 血的教训（最重要，先看这条）

1. **这个模块真正的病，不是任何单个函数写错，而是「同一类事实存了多份副本」。** 审阅者原话：
   > 「这不是『一个模块』，是『一个模块 + 一份逐年加固的防御工事』。」
   「哪个文件读失败了」一度由 **6 个模块级变量**分别记录；「操作互斥」有 **3 套并行实现**；
   「哪些键该写」有 **4 套判据**；「恢复范围」有 **2 套来源**；「失败怎么还原」有 **2 处近乎逐字重复**。
   后果是结构性的：**改一处必漏另一处** —— 12 轮里有 9 次「声称修了、实际只改一半」全是这个原因。

2. **「读失败」绝不能当成「不存在」。** 这是本项目出现频率最高的伪装 bug，在**账本、备份、锁**三条路径上都中过：
   读不到 → 当作没有 → 静默跳过保护 → 照常覆盖。正确写法见 §2.6。

3. **写操作三条铁律**：覆盖前必须能反悔 → 反悔失败必须如实说 → 被保护的东西必须真的被保护（`.prev` 只写不读 = 没有反悔）。

4. **加固本身会变成新的风险源。** 12 轮里 **9 个 bug 是我在"修 bug"时引入的**（v1.2.2 到 v1.3.0 每一个版本都有）。
   教训：每加一层保护，就必须同时问「这层保护失效时会发生什么」。

5. **用户的真机不是测试机。** 上面所有问题里，真正上过用户服务器的只有 2 条，其余全部在交付前被拦下 ——
   拦住它们靠的不是「我想得更仔细」，而是**三个不同角色的独立盲审**（见 §6）。

6. **失败之后继续、还是停下？判断标准不是「这个动作重不重要」，而是「这次失败会让用户失去什么」。**
   v1.2.8 把「另存上一份回档账本」的失败处理成 **fail-open**（只 warn 一句，然后照常写新账本），
   代码注释里写的理由是「不要因为一个辅助动作失败就阻断主操作」—— **判断做反了**。
   账本是**唯一**的撤销点，覆盖即永失（服务器上没有它的副本，Foundry 也没有删除/恢复文件的 API）；
   而 fail-closed 的代价只是「这次没做成，修好磁盘/权限后重试即可」。
   > 正确判据：**失去唯一副本 / 唯一撤销点 → 必须停下并说清；只损失一次便利 → 可以继续但必须出声。**

   这条来自外部审阅第 4 条，是四条里唯一一条**我的设计取舍本身错了**的（不是写错，是选错）。

7. **「善意的兜底」会把一种合法输入解释成另一种语义。** `buildSelection()` 里那句
   「空 custom 视为全部（防止恢复什么都没做）」，看着是在保护用户，实际把
   「取消所有模块 + 只保留模组启用状态」这个**合法组合**（勾选数同样是 0）当成了「全部同步」——
   用户明确不想被覆盖的模块设置被整份写掉。
   > 语义只允许一处说了算：范围只由 `mode` 决定，「允不允许空」只由保存动作（`saveScopePref`）决定。
   > 写兜底之前先问：**这个「异常输入」，有没有可能只是我没考虑到的正常需求？**

8. **外部审阅的价值不在「找出更多条」，而在「指出模型层面的病」。** 八轮里报出最多条的是盲审 subagent
   （19 条），但质量最高的是外部审阅那份**只有 4 条**的报告 —— 它每一条都不是「某行写错了」，
   而是「同一件事在 A 处和 B 处语义不同」。这类问题**测试抓不到**（测试只验单条路径），
   **作者自审也抓不到**（写的时候脑子里只有一个场景）。

9. **v1.3.4 撞上的是同族病的另一种形态：一条关系被拆成两半，分属两个文档系统。**
   §0 第 1 条讲的是「同一个值存了多份副本」；这里是**一个关系存了两个载体**：
   「哪个合集包放在哪个文件夹里」= 映射存 `core.compendiumConfiguration`（**Setting**）
   ＋ 本体存 `game.folders` 里 `type === "Compendium"` 的 **Folder 文档**。
   模块从前到后只搬了映射、**从头到尾没碰过本体**（全文 grep `Folder|compendium|game.folders` = 0 匹配）。
   后果不是「值写错了」，是**指针指向了不存在的对象** —— 而核心对此**不报错**：
   `client/documents/collections/compendium-collection.mjs:161-163`

   ```js
   get folder() { return game.folders.get(this.config.folder) ?? null; }
   ```

   查不到就当作「这个包没有文件夹」（该字段官方定义本就允许 null，同文件 `:95-96`），包静默散到顶层。
   > 判据：**同步/迁移任何东西之前，先列出「这条事实由几个载体共同表达」。**
   > 带走了「A 指向 B」，就必须同时问：**B 本身带走了吗？**
   > 用户当时的描述「**包都在，就是没归位**」已经把层次说清了：数据没丢，断的是关系。

## 2. 正解存档（照抄这些，别再发明）

### 2.1 世界级设置怎么读、怎么写

```js
// ❌ 错的：game.settings.set/get 对未注册的键直接抛错
//    "xxx is not a registered game setting"（出处 client/helpers/client-settings.mjs:271）
// ✅ 对的：走「存储全集」——它是一个 WorldCollection，可枚举、可批量写
const store = game.settings.storage.get("world");
for (const doc of store.values()) {
  if (doc.user) continue;          // user 级设置（玩家个人偏好）不参与同步
  // doc.key 形如 "命名空间.键"，doc.value 是**已解析好的对象**（JSONField 的 initialize 里做了 JSON.parse）
}
// 写：Setting 文档静态批量方法（注意 value 必须自己 JSON.stringify）
await Setting.updateDocuments([{ _id, value: JSON.stringify(obj) }]);
await Setting.createDocuments([{ key, user: null, value: JSON.stringify(obj) }]);
await Setting.deleteDocuments([id]);
```

**出处（换 Foundry 版本时以此核对）**：
- 存储全集与作用域：`client/helpers/client-settings.mjs:42-47`（CLIENT→localStorage，WORLD/USER→世界集合）
- `WorldSettings` 只有 `getSetting/getItem`，枚举要 `[...store.values()]`：`client/documents/collections/world-settings.mjs:35-47`
- `Setting.value` 是 `JSONField`：`common/documents/setting.mjs:45`；读出来是对象、写进去要字符串：`common/data/fields.mjs:3002-3027`
- 权限：`Setting.canUserCreate` 要 `SETTINGS_MODIFY`；`core.permissions` **仅全权 GM**；助理 GM 只有 9 个 `core.*` 白名单键（`common/documents/setting.mjs:57 / 65-93`）
- **权限失败的形态是「抛错」**，不是静默过滤（用户世界实测日志：`User Player2 lacks permission to update Setting`）

### 2.2 快照 / 账本 / 锁的布局，与「全局 vs 世界」作用域 ⚠️

| 文件 | 落在哪 | 作用域 | 谁能保护它 |
|---|---|---|---|
| `world-snapshot-master.json` | `Data/modules/<id>/storage/` | **全局**（所有世界共用一份） | 必须用**全局锁** |
| `world-snapshot-master.prev.json` | 同上 | 全局 | 同上 |
| `apply-log-<世界ID>.json` | 同上 | 世界 | 世界锁 |
| `operation-lock.json` | 同上 | 全局单槽 | 见 §2.7 |

**踩过的坑**：锁的判据只看 `worldId`，而被保护的主快照是**全局单文件** →
两个 DM 各开一个世界同时点「存主世界」，两边 worldId 不同 → **双方都放行** → 都写同一个文件、都报成功，
可以造出「主快照 = A 的内容、`.prev` = B 的内容」这种中间态，而 `.prev` 只有一代。

```js
// ✅ 正解：锁的作用域必须与被保护的资源匹配
const isGlobalOp = (opName === "snapshot");          // 写主快照 / 导入设为主快照 = 全局资源
const crossWorldConflict = isGlobalOp || (l?.scope === "global");
if (effExpires > now && (crossWorldConflict || l.worldId === currentWorldId()) && !(sameOwner && samePage)) {
  return { ok: false, holder: l };                    // 拒绝
}
```

⚠️ **另一条必须知道的前提**：**卸载模块会连 `storage/` 一起被递归删除**，Foundry 对 `persistentStorage` 没有例外
（出处 `dist/packages/package.mjs` 的 `uninstall` → `fs.rm(dir, {recursive:true, force:true})`；只有 `dist/packages/installer.mjs` 的安装/更新会保留）。
→ **升级永远用覆盖文件，不要「先卸载再装」**；要留底就导出到用户自己电脑。

### 2.3 覆盖前的「内容体检」——三条路径共用同一条判据，且读不到就拒绝

**踩过的坑**：体检只写在「存主世界」按钮里 → 导入 →「设为主快照」这条路径**完全没有体检**，
一份空快照就能把 8.8MB 基准换掉；之后再存一次，唯一那份 `.prev` 也被覆盖 → **服务器上再无完整副本**，
而界面还在说「上一份已备份为 X」。更糟的是体检依赖界面缓存，读不到时只 `console.warn` 后照常覆盖。

```js
const MASTER_MIN_ITEMS = 20;        // 少于这么多项：不可能是完整的主世界配置
const MASTER_SHRINK_RATIO = 0.3;    // 只剩不到三成：典型的「选错了世界」
let masterOverwriteAck = null;      // ⚠️ 记「已确认的那一份有多少项」，不要用 true/false

async function preflightMasterOverwrite(newCount, label) {
  let oldCount = 0;
  try {
    const { text, error } = await storageRead(MASTER_FILE);
    if (error) return { ok: false, reason: "readError", detail: error };   // 读不到 = 拒绝覆盖
    if (text) oldCount = parseSnapshot(text).settings.length;
  } catch (e) {
    return { ok: false, reason: "readError", detail: (e?.message || String(e)) };  // 内容不合法 = 拒绝
  }
  if (!oldCount || newCount >= oldCount) return { ok: true, oldCount };
  if (masterOverwriteAck === newCount) { masterOverwriteAck = null; return { ok: true, forced: true }; }
  if (newCount < MASTER_MIN_ITEMS || newCount < oldCount * MASTER_SHRINK_RATIO) {
    masterOverwriteAck = newCount;
    return { ok: false, reason: "tooSmall", oldCount, newCount };
  }
  return { ok: true, oldCount };
}
```

**三条要点**（对应三次翻车）：
1. **判据读服务器上的真实文件**，不读界面缓存 —— 缓存拿不到时「判据不可用 → 反而更容易覆盖成功」是反的；
2. **确认按内容绑定**（`masterOverwriteAck === newCount`）—— 用 `true/false` 的话，被警告后关掉面板、换个世界再点就失效了；
3. **体检自身抛错也要取消本次保存**，不能 `catch { console.warn }` 后继续覆盖。

### 2.4 恢复的三件套：先记账 → 批量写 → 失败回滚

```js
// ① 必须先写账本（写不进就一个设置都别动，并打标记让上层别谎称「已自动回滚」）
let logOpId = null;
try { logOpId = await writeApplyLog(prevMap, afterMap); }
catch (e0) { e0.__notStarted = true; throw e0; }

// ② 批量写（逐条 await 的话 1300 项就是 1300 次往返）
const createdByKey = new Map();
try {
  if (updates.length) await SettingDoc.updateDocuments(updates, {});
  if (creates.length) {
    const made = await SettingDoc.createDocuments(creates, {});
    for (const d of (made ?? [])) createdByKey.set(d.key, d._id ?? d.id);   // 记下来供失败还原精确删除
  }
} catch (e) {
  // ③ 失败还原：把已碰过的键批量还原；还原也失败必须如实上报（别用一句「已回滚」盖过去）
  let rollbackErr = null;
  try { /* 用 before 快照批量还原 */ } catch (e2) { rollbackErr = e2; }
  e.__rollbackFailed = !!rollbackErr;
  throw e;
}

// ④ 写完才标记账本应用于「已完成」（否则中途崩掉会被讲成「你又改过」）
await markLogApplied(logOpId);
```

**上一层的提示必须分三态**（三句话对应三种真实情况）：

| 标记 | 用户看到的话 |
|---|---|
| `__notStarted` | 「恢复没有开始：账本写不进服务器…世界的设置一个字都没动」 |
| `__rollbackFailed` | 「恢复失败，且自动回滚没能完成（世界可能停在中间状态）。**请不要刷新页面**」 |
| 其他 | 「恢复失败，已自动回滚到恢复前的状态」 |

### 2.5 ⚠️ 模组启用列表必须**合并写入**，不能整串覆盖

**这是本项目最容易被忽略、后果最像「把世界写坏」的一条。**

```js
// ❌ 错的：整串覆盖
//    快照来自「当时没装模组 M 的世界」→ 恢复进装着 M 的世界 → 配置里没有 M 的键
//    → 刷新后 M 的脚本不被加载（= M 被静默关掉），而界面报告「同步成功」
// ✅ 对的：以当前世界打底，只覆盖快照里显式存在的键
function mergeModuleConfig(snapshotVal, currentVal) {
  const cur = (currentVal && typeof currentVal === "object") ? currentVal : null;
  const merged = cur ? { ...cur, ...snapshotVal } : snapshotVal;
  return { ...merged, [MODULE_ID]: true };   // 本模块自己永远保留为启用
}
```

**判据出处（已坐实）**：
- 页面注入：`dist/server/views/view.mjs` 的 `_getStaticContent` **只注入 `moduleConfig[id] === true`** 的模组
- 发送世界数据：`dist/packages/world.mjs` 里 `e.active = l[e.id] ?? false` —— **缺键 = false = 不激活**

⚠️ 配套：账本记的必须是**实际写入的值**（合并后的），不是 `diff.changed[i].to`（快照原值），
否则漂移检测会拿原值跟当前值比 → 永远误报「你又改过」。

### 2.6 「读失败 ≠ 不存在」——把状态随结果一起返回，不要用模块级变量

```js
// ✅ storageRead 返回 { text, error }：404 才是「确实不存在」，其余都带原因
async function storageRead(name) {
  const url = foundry.utils.getRoute(norm(STORAGE_DIR) + "/" + name);   // ⚠️ 必须带路由前缀
  let r;
  try { r = await fetch(url, { cache: "no-store" }); }
  catch (e) { return { text: null, error: "无法连接服务器（" + (e?.message || e) + "）" }; }
  if (r.status === 404) return { text: null, error: null };             // 唯一能确认「不存在」的分支
  if (!r.ok) return { text: null, error: "服务器返回 HTTP " + r.status };
  try { return { text: await r.text(), error: null }; }
  catch (e) { return { text: null, error: "读取响应内容失败" }; }
}

// ❌ 反例（本项目踩过）：单个模块级变量 let storageLastError = null;
//    一次操作会连读 锁 → 主快照 → 账本 → 旧账本，后一次读覆盖前一次，
//    于是「刚读完 404、下一句又读到 5xx」这类交错会让所有错误提示说错原因。

// ❌ 另一个反例：只解构 text、丢掉 error（本项目在 openSyncPanel 里正是这样）
const { text } = await storageRead(MASTER_FILE);   // storageRead 对 5xx 不抛异常 → 下面的 catch 永远不会执行
// → 界面静默退化成「只有当前世界已有的模块」，用户可能保存一个残缺的恢复范围
```

### 2.7 操作锁的正确写法（尽力而为，但**失效时必须出声**）

```js
const LOCK_FILE = "operation-lock.json";
const LOCK_TTL_MS = 120000;
const lock = {
  operationId: foundry.utils.randomID(),
  op: opName,
  scope: isGlobalOp ? "global" : "world",   // ⚠️ 作用域必须匹配被保护的资源（见 §2.2）
  worldId: currentWorldId(),
  userId: game.user.id,
  owner: myOwner(),                          // 浏览器会话标识（sessionStorage，刷新不变）
  pageToken: myPageToken(),                  // 页面标识（内存，刷新即变）→ 防「刷新后认领自己的旧锁」
  startedAt: new Date(now).toISOString(),
  expiresAt: now + LOCK_TTL_MS
};

// 读侧判据：① 世界/全局作用域匹配 ② 页面级归属 ③ 到期时间取读侧上限
const startedMs = Date.parse(l?.startedAt || "") || 0;
const hardCap = startedMs ? startedMs + 2 * LOCK_TTL_MS : 0;
const effExpires = hardCap ? Math.min(Number(l?.expiresAt) || 0, hardCap) : (Number(l?.expiresAt) || 0);
```

**三个必须记住的点**：
1. **读侧要给到期时间加上限**：`expiresAt` 由写锁那一方用**它自己的本机时钟**算出，时钟快进 / 手工改锁文件 /
   还原一份旧锁都可能塞进极大值 → 其他 GM 被**永久拒绝**，而提示还在说「约 2 分钟自动解锁」（假话）。
2. **写锁失败不能把整个操作拖死**，但**必须提示**「本次未做互斥检查」—— 静默放行等于让两个 GM 各写各的账本、
   撤销点互相覆盖，而界面上看不出任何异常。
3. **回读校验只认「明确的、非自己的 operationId」**：`JSON.parse(null)` 不抛错、返回 `null`，
   用 `l2?.operationId !== 自己的` 判会把自己刚写的锁判成「别人的锁」。

### 2.8 回档账本：读和用必须在同一把锁里

**踩过的坑**：账本在**锁外**读、锁内用。从「读到账本」到「拿到锁」之间，别人完全可能完成一次恢复 ——
主账本已换成新的 `prev/after`，而本流程仍按**旧账本**覆盖世界（用旧值抹掉更近的值），
随后的 `markLogRolledBack()` 还会把**新账本**标成「已回档过」：用户唯一的撤销点被标成用过的。

```js
const r = await withOpLock("rollback", async () => {
  const fresh = await readApplyLog();                       // 进锁后重读
  if (applyLogReadError) return { readError: applyLogReadError };
  if (fresh?.prev) {
    if (log?.opId && fresh.opId && String(fresh.opId) !== String(log.opId)) {
      return { stale: true };                               // 等锁期间被换过 → 取消
    }
    log = fresh;
  }
  …
});
```

**另一条（回档最常见的伤人方式）**：账本记 `present:false` 的键 = 「那次恢复时它本来不存在（是恢复过程创建的）」，
回档时会 `deleteDocuments` 删掉它。但如果用户在恢复之后**真的把它配起来了**，这一删**没有任何副本**
（`before` 只在内存里，账本的 `after[key]` 记的还是当初写进去的值）。
→ 修法：比对 `after[key]` 与当前值，不一致就 `continue` 保留不动，并在回档报告里单列「这 N 项是你在恢复之后又改过的，已原样保留」。

### 2.9 ⚠️「引用」和「被引用的文档」是两件事，必须一起搬（v1.3.4）

**踩过的坑**：`core.compendiumConfiguration` 形如 `{包id: {folder: "夹id"}}`（记录「哪个包在哪个文件夹」），
它不在 `EXCLUDE_DEFAULT` 排除表里，每次都跟着快照走；而**文件夹本体是 Folder 文档**

```js
// ② 两步法：先全部建在顶层，再补父子关系（父夹可能还没建，先引用会失败）
const toCreate = snap.compendiumFolders
  .filter(f => !game.folders.has(f._id))        // 按 _id 判重：已有同 id 绝不动
  .map(f => ({ ...f, type: "Compendium", folder: null }));
await FolderCls.createDocuments(toCreate, { keepId: true });   // ⚠️ keepId 是命门
await FolderCls.updateDocuments(snap.compendiumFolders.map(f => ({ _id: f._id, folder: f.folder })));
```

**`keepId` 是这类迁移的唯一命门** —— 出处 `common/abstract/document.mjs:454-460`：


不传它 = 夹子全建成**新 id**，`compendiumConfiguration` 里那些引用**一个都对不上**，
症状和「什么都没搬」一模一样（而且更难查，因为夹子明明建出来了）。

## 3. UI 正解

### 3.1 ⭐ 按钮注入：**优先用官方 render hook，轮询只是兜底**

> 用户原话要求把这条写下来：「那个稍微不好的图标轮询，改成常驻的写法」

**两个阶段的结论，别搞混：**

| 阶段 | 做法 | 评价 |
|---|---|---|
| 早期（简单陷阱篇） | `setInterval(1500)` 常驻轮询 + `insertAfter(锚点)` | **能跑，但下策**。当时的关键教训是「严禁挂上就 `clearInterval`」——切场景会重建控制栏 DOM，停了按钮就消失 |
| 现在（本条） | `Hooks.on("renderSidebar", …)` 官方渲染钩子 + **有限重试兜底** | ✅ 正确做法：**事件驱动，不再轮询** |

**为什么轮询是下策**：① 每秒都在查 DOM（虽然轻，但是常驻开销）；② 只能"事后补救"，DOM 重建到下一次轮询之间有窗口期；
③ 与 FVTT 的渲染生命周期毫无关系，纯粹靠猜。

**hook 名怎么来的（别猜，能推）**：
- `client/applications/api/application.mjs:1226-1233` `#callHooks(hookName, hookArgs, parentClassHooks)`
  里 `Hooks.callAll(hookName.replace("{}", cls.name), this, ...hookArgs)`
- 同文件 render 事件的 `hookName` 是 `"render"`（见 `:523` 一带的 debugText "After render"）
- 侧边栏类名是 `Sidebar`（`client/applications/sidebar/sidebar.mjs:23` `export default class Sidebar extends HandlebarsApplicationMixin(ApplicationV2)`）
- → **`renderSidebar`**。切页签另有 `Hooks.callAll("changeSidebarTab", ui[tab])`（同文件 `:250`）

```js
// ✅ 正确写法：模块顶层注册（关键！见下面的坑），事件驱动 + 有限重试兜底
function mountSidebarButton() {
  const $anchor = $('button[data-tab="settings"]').first();   // 锚点：官方设置页签
  if (!$anchor.length) return false;                          // 锚点没出现，交给重试
  if ($("#" + BTN_ID).length) return true;                    // 已经挂上，什么都不做
  const $li = $(`<li><button id="${BTN_ID}" class="ui-control plain icon ${BTN_ICON}"></button></li>`);
  $anchor.closest("li").after($li);
  if (!$("#" + BTN_ID).length) return false;                  // ⚠️ 回读校验：插了不等于插上了
  return true;
}
Hooks.on("renderSidebar", () => { if (game.user?.isGM) mountSidebarButton(); });
Hooks.on("changeSidebarTab", () => { if (game.user?.isGM) mountSidebarButton(); });

// 兜底：万一 hook 没触发（别的模块重建了侧栏），最多重试 8 次，挂上即停
const BTN_RETRY_MAX = 8;
function ensureSidebarButton(attempt = 0) {
  if (mountSidebarButton()) return;
  if (attempt >= BTN_RETRY_MAX) { console.warn("…已放弃自动挂载，可从「设置 → 模组设置」进入"); return; }
  setTimeout(() => ensureSidebarButton(attempt + 1), 1000);
}
```

**⚠️ 这个坑最致命，务必记住**：

> **hook 必须在模块加载期（文件顶层）注册，等 `ready` 再注册就错过首次渲染了。**

出处：`client/game.mjs:772` `this.initializeUI()` 在 `:787` `Hooks.callAll("ready")` **之前**；
`:992` `ui.sidebar.render({force:true})` —— 侧边栏渲染早于 ready。

**另一条同类坑**：`window.xxx = game.user?.isGM ? …` 这种语句**不能写在模块顶层** ——
`globalThis.game` 只在 `DOMContentLoaded` 回调里创建（`public/scripts/foundry.mjs:181079-181097`），
而模组脚本是 `<script type="module">`（`templates/views/layouts/main.hbs:28`）= defer 语义、**早于 DOMContentLoaded 执行**
→ 顶层读 `game` 抛 ReferenceError，那个控制台入口**从来就没挂上过**。正确位置是 `Hooks.once("ready", …)`。

### 3.2 图标：三种用法，别混

| 场景 | 正确写法 | 踩过的坑 |
|---|---|---|
| 侧边栏 / 场景栏按钮 | 类名照抄官方：`class="ui-control plain icon fa-solid fa-arrows-rotate"`，图标名从**官方模板**里抄 | 自己拼类名 → 渲染成空白小方块 |
| Dialog 按钮 | `buttons: { ok: { icon: '<i class="fa-solid fa-check"></i>', label: "确定" } }` —— **必须是 HTML 字符串** | 直接写 `"fa-solid fa-check"` 字符串 → 渲染成空白 |
| 独立图标按钮（无文字） | **不要做** | 单独一个 fa 图标渲染成空白小方块 |

**图标名从哪来**：① 官方模板（`templates/sidebar/tabs.hbs` 等）；② 用户世界导出的 JSON 里 grep（`0 样本 = 404 风险，禁用`）；
③ 本机 FVTT 的 `resources/app/icons/` 实际列目录。

### 3.3 面板与主题（详细版见《血的教训-CSS面板配置篇》）

## 5. 铁律（本次沉淀）

1. **写操作三条**：覆盖前能反悔 → 反悔失败如实说 → 「有备份」必须真的能取回（只写不读的备份等于没有）。
2. **「读失败」永远不等于「不存在」** —— 把原因随结果返回，别用模块级变量攒状态。
3. **同一件事有几条路径，就要点几次名** —— 有 N 条入口，就检查 N 条都过了同一个判据。
4. **锁的作用域必须配得上数据模型 —— 配不上就改承诺，别改实现细节。** v1.3.1 曾按「全局锁 / 世界锁」
   分作用域，但两类锁共用同一个 `operation-lock.json`：**一个标量文件表达不了「一把全局锁 + 多把世界锁」**，
   B 世界开始恢复会覆盖 A 的锁记录，B 先释放后 A 世界的第二位 GM 读到「没有人在操作」
   → 两个恢复同时写同一个世界，正是这把锁要防的事。
   v1.3.3 改为**所有同步写操作全局串行**（用户拍板）：同步是低频管理动作，没有并发的必要，
   全局互斥换来「行为可推理」。锁失效时必须出声。
   > ⚠️ **本条第 4 项的旧表述（「全局文件用全局锁」）已被推翻** —— 只把「读主快照」标成全局锁
   > 并不能解决覆盖问题，因为**锁文件本身仍是单份**。要么把锁改成多世界锁表（`{global, worlds:{}}`，
   > 但 Foundry 持久化存储没有 CAS，文件级读改写竞态仍在），要么放弃并行承诺。本项目选了后者。
5. **整串覆盖前先问：缺键意味着什么？**（`moduleConfiguration` 缺键 = 模组被关掉）
6. **加固的每一层都要问「这层失效时会发生什么」** —— 9 次自伤都是这么来的。
7. **审阅要换角色，不要换工具**：破坏者 / 接手者 / 文档对现实，三个视角一起下，比再读十遍代码有用。
8. **真机不是测试机**：先跑断言（本模块到 v1.3.4 已有九套脚本共 635 项，见 §6），再交给用户。
9. **每轮审查的错误与修法必须落成 MD 存档**（本机约定见 `FVTT技术资料\审查记录\`），否则下一轮会重复问同一件事。
10. **交付前跑一遍《血的教训-代码审阅自检清单篇》的 14 项**。
11. **失败策略：先问「这次失败会让用户失去什么」。** 失去唯一撤销点 / 唯一副本 → **fail closed**
    （停下，并说清「世界一个设置都没改」以及为什么）；只损失一次便利 → 可以继续，但必须出声。
    **「辅助动作失败就继续」是一个错误的默认值。**
12. **「你看到的目标值 = 实际写入的值 = 账本记下的值」是不变量。** 差异检测、实际写入、回档账本
    三处必须共用同一条「有效目标值」规则（本项目抽成 `keepSelfEnabled(key, 快照值, 当前值)`）。
    只改一处的后果是**永久假差异**：恢复 → 刷新 → 报完全一样的差异 → 再恢复，永不收敛，
    用户会以为这个模块坏了。
13. **测试之间共享的全局状态会掩盖真实的互斥行为。** 本项目测试脚本的 `files` Map 跨用例共享，
    是「残留的锁把后续用例挡在门外」才把它暴露出来的 —— 反过来想：如果残留的效果是
    「本该被挡却放行」，测试**永远不会发现**。每轮改锁 / 改互斥，先显式清一次共享状态再跑。
14. **改完必须回读验证，不能只信自己的改动。** 本项目出现过 8 次以上「声称修了、实际只改了一半」：
    声称改了注释却漏了代码、改了函数体却没改参数名、把 `to` 的规则改了三处中的一处。
    → 每处改动后 grep 回读，并用断言把「签名」与「函数体」绑在一起。
15. **同步一条「关系」之前，先数清它有几个载体。** 带走了「A 指向 B」不等于带走了 B 本身 ——
    v1.3.4 的「包 ↔ 文件夹」就是这么漏的（映射在 Setting、本体在 Folder 文档）。
    → 迁移引用时三连问：**被指向的文档带了吗？id 保住了吗（`keepId: true`）？目标世界查不到时会怎样（静默 null 还是报错）？**
16. **「静默返回 null」是同步类工具最危险的失败形态。** 核心为了容错把「引用不到」定义成「没有」，
    于是「丢了数据」与「本来就没有」在数据上长得一模一样，**日志、报错、UI 全都没有任何异常**。
    → 凡是要保证引用完整性的地方，必须自己显式检查「这个 id 在当前世界解析得到吗」，不能指望核心报错。
17. **一个「空即无效」的判据，在新增一个维度之后必须重审。** `validateApplyLogEntry()` 的
    「`prev` 为空 ⇒ 撤销点无效」在只有设置同步时是对的；加入文件夹维度后，
    「设置全同、只同步文件夹」这种合法情况会被它静默判废，丢掉那唯一一个撤销点。
    → 任何 `if (!x) return invalid` 都要问：**x 为空，是真的无效，还是我没考虑到的新场景？**

## 6. 给下一个接活的智能体

- 这个模块的代码有 **3277 行**（v1.3.4 实测；v1.3.3 是 2955 行，每版都在涨），其中大约一半是**防御性代码**（每一条背后都是一次真实翻车）。改动前先读注释，
  那些 `vX.Y.Z（第 N 轮盲审 Sx）` 的标记就是「这里死过人」的墓碑，**别把它们当废话删掉**。
- 改动**单轮不超过 10 处**；每改一处立刻写断言（本项目做法：`vm.createContext` 加载真实脚本 + 打桩，见 `%TEMP%\wsync-v1xx-test.js`，
  目前九套脚本共 **608 + 27 = 635 项**断言；v1.3.4 新增的 `_tests\assert_folders.js` 是 27 项，只覆盖新增的文件夹逻辑）。**优先写行为断言，不要只写文本断言** —— 文本断言只能证明「代码里有这句话」，
  行为断言才能证明「它真的这么做了」（本项目正是靠行为断言抓到过一次「头注释声称改了、代码只改了一半」）。
  另外：新加的超时/并发能力要用**探测式**写法（如 `typeof AbortController !== "undefined"`），
  否则 `vm` 沙箱里没有该 API 会让全部测试直接崩。
- **审阅期间冻结代码**：一次盲审的审阅者原话是「审阅对象是移动靶」—— 审阅者读的过程中代码在被改，行号全部漂移，复核成本翻倍。
- 用户明确的收手标准（值得继承）：**「只修会伤到你的，其余记档」** —— 会丢数据/永久卡死的修，提示措辞/极端场景防护的记档并写明影响范围。
  否则会陷入「越修越多、越修越怕」的循环。
