# 血的教训 · 第三方同步模块并发写设置篇

> ## ⚠️ 文件说明（务必严肃阅读）
>
> 本文件记录一次**真实发生、由第三方模块造成、潜伏半年才被发现**的数据污染：
> 用户世界的 521 个设置键各自拥有 2~5 份重复的 Setting 文档，总共多出 1221 份垃圾数据。
>
> **如果你即将装「世界设置同步 / 复制环境 / 批量导入设置」类模块，或者要写批量写设置的代码，先读本文件。**

---

## 0. 血的教训（最重要，先看这条）

1. **不是所有重复都会被立即发现**：官方读设置用 `find` 取**第一份**，所以多出来的副本可以静静地躺半年，功能照常、界面无异常。
2. **批量写设置时，`promises.push(game.settings.set(...))` 是危险写法**：同一个键被并发写两次时，两次都在「查不到已有文档」的状态下各自创建 → 一个键两份文档。
3. **判断「谁写的」不要靠猜，靠时间戳**：Setting 文档自带 `_stats.createdTime`。把每份文档的创建时间按小时聚合，元凶的行踪一目了然。

---

## 1. 案例复盘：521 个键的重复副本

### 1.1 现象

用户在 Foundry v13.351 世界（约 2700 份 Setting 文档）里跑诊断脚本，发现：

| 指标 | 数值 |
|---|---|
| 真重复组（同 key + 同 user 有多份） | **521 组** |
| 涉及文档总数 | **1742 份** |
| 份数分布 | 2 份 × 63 组 / 3 份 × 218 组 / 4 份 × 238 组 / 5 份 × 2 组 |
| 内容完全相同 | 497 组（95%） |
| 内容有差异 | 24 组 |
| 副本创建时间 | **同一组内所有副本精确到秒完全相同** |

### 1.2 关键线索：同一秒创建、值还不一样

```
levelsautocover.tokensProvideCover   [4 份 · 全为 2026/2/20 04:07:07]
   值：false  ||  true  ||  true  ||  true

auraeffects.defaultVisibility        [4 份 · 全为 2026/2/20 04:07:08]
   值：true   ||  false ||  false ||  false

always-hp.resourcename               [4 份 · 全为 2026/2/20 04:07:08]
   值："attributes.hp.value" || "attributes.hp" || "attributes.hp" || "attributes.hp"
```

两条推论：

- **时间完全相同** → 不是「反复导入几次」（那会散落在不同时间），而是**同一次操作里并发写入多份**。
- **值不同** → 写的人手里有**多个来源**（一个是当前世界的值，其余是默认值/跨世界通用值），并且把它们**同时**提交了。

### 1.3 元凶定位（时间戳直接排除法）

副本创建时间只集中在几个时刻：`2026/2/20 04 时`（518 份）、`2026/2/21 17 时`（1024 份）、`2026/5/23 16 时`（195 份）、`2026/3/5` 与 `3/9`（共 5 份）。

用户当时自己写的模块是**当年 9 月**才做的 —— 时间上根本对不上，**与自己的模块无关**。
真正的时间点全部落在用户安装 `world-setting-sync`（theripper93，v2.0.0）之后。

## 2. 根因：并发写同一个键

### 2.1 病灶代码

`world-setting-sync/scripts/app/SettingsSync.js:442-476`：

```js
const promises = [];

if (type === "agnostic" || type === "all") {
    for (const [namespace, diff] of Object.entries(changes.settings.agnostic)) {
        for (const [key, value] of Object.entries(diff)) {
            promises.push(game.settings.set(namespace, key, value));   // ← 立刻发起，不 await
        }
    }
}

if (type === "system" || type === "all") {
    for (const [namespace, diff] of Object.entries(changes.settings.system)) {
        for (const [key, value] of Object.entries(diff)) {
            promises.push(game.settings.set(namespace, key, value));   // ← 同一个键可能又来一次
        }
    }
}

this.close(true);
await Promise.all(promises);          // ← 上千个写操作同时飞出去
```

### 2.2 为什么这样会造出重复文档

`game.settings.set(namespace, key, value)` 的内部流程是「**先找再写**」：

```
getSetting(key, user)  →  找到就 update  /  没找到就 create
```

并发时两次调用**同时进入查找阶段**，谁都还看不到对方将要创建的文档 → **两边都走 create 分支** → 同一个键出现两份文档。
`changes.settings.agnostic` 与 `changes.settings.system` 里键重叠得越多，重复的份数就越多 —— 这正好解释了「2 份 / 3 份 / 4 份」的分布，也解释了**同一组副本的值为什么不一样**（一份来自 agnostic 库，一份来自 system 库）。

### 2.3 波及范围为什么是上千个键

`world-setting-sync/scripts/SettingsCompiler.js:28-32`：

```js
get worldSettings() {
    return Array.from(game.settings.settings)      // 注册表里「所有」设置定义
        .map((s) => s[1])
        .filter((s) => s.scope === "world");
}
```

它编译的是**整个注册表**（该世界装了 210+ 个模块），一次「同步全部」就可能触及上千个键 —— 与实测的 1742 份文档规模吻合。

## 3. 影响评估与处置

### 3.1 影响（为什么可以潜伏半年）

- **官方读设置 `find` 取第一份** → 功能不出错；
- 但代价是：① 数据臃肿（世界文件、每次备份/导出都带着）② 若有模块用遍历而非 `find`，会读到旧值 ③ 若某模块删自己的设置时只删一份，另一份永久残留。

### 3.2 处置（诊断 → 备份 → 删除，三步）

1. **诊断**（只读）：按 `key + user` 分组，输出重复组数、份数分布、各份创建时间、内容是否相同。
   ⚠️ 判据必须是 **key + 归属者**两个维度 —— Foundry 允许「同一个键有 1 份世界级 + 每个玩家各 1 份个人级」，只按 key 分组会把正常情况误报成重复。
2. **备份**：把每组的完整信息（键、份数、id、创建时间、值）序列化后 `game.clipboard.copyPlainText(...)`，让用户粘到本地文件存好。
3. **删除**：`foundry.utils.getDocumentClass("Setting").deleteDocuments(ids, {})`，**删每组第二份及以后、保留第一份**。
   - 保留第一份是安全的：官方 `game.settings.set` 永远更新「找到的第一份」，所以**第一份永远是最新值**，后面的副本从那一刻起就是死的。
   - 给 8~9 秒缓冲 + 明确告知「按 F5 可取消」，再真正执行。

### 3.3 防止复发

- **关掉/卸掉造成问题的那个同步模块**（本例：`world-setting-sync`），否则清理完它下次同步又会造新的；
- `forien-copy-environment` 的导入路径里也有 `storage.setItem(data.key, data.value)`（`scripts/core.js:546`），属于同类风险，一起注意。

## 4. 铁律

1. **批量写设置不要 `push(game.settings.set(...))` 后 `Promise.all`** —— 串行 `for...await`，或先批量查询现有文档再 `updateDocuments`/`createDocuments`。
2. **一个键写一次**：同一批里若会出现同名键（多来源合并），**先合并去重再写**。
3. **判断「是不是重复」要看 `key + user` 两个维度**，只看 key 会把正常的多用户设置误判。
4. **查元凶看 `_stats.createdTime`**，按小时聚合；同一秒创建的多份 = 并发写入，不同时间创建的多份 = 反复导入。
5. **清理前必须留备份**，清理要保留「官方实际读取的那一份」（第一份），并给用户反悔窗口。
6. **第三方同步类模块装之前先问三个问题**：它写哪些键？怎么写的（并发还是串行）？出问题能不能一键回退？—— 本例三个答案分别是「全部」「并发」「不能」。

---

## 5. 给下一个接活的智能体

- 用户世界里出现「数据看着不对但功能正常」的现象时，**先怀疑历史遗留的批量写入**，别急着改自己的代码；用 `_stats.createdTime` 分组，十分钟就能定性。
- 发现是第三方模块干的，要给出**可指认的代码行号**，不要只说「可能是某个模块」。
- 用户的服务器 `http://146.56.232.12:30000` 是 HTTP 环境：剪贴板必须用 `game.clipboard.copyPlainText`，浏览器原生 `navigator.clipboard` 是 undefined。
