十二、权限转交 / 临时操控类（附身符这串硬骨头的总结）

凡是"让玩家临时操控一个原本不属于他的 token"（附身、魅惑、临时召唤同盟、夺取载具）都会连环踩到下面这几个，每一个都让人以为是别的问题，实则独立。出之前逐条对。

1. socket 频道名：world.* 不会被广播，必死。
   game.socket.emit/on 只转发 module.<id> 和 system.<id> 两种命名空间。写 "world.possessionCharm" 这种自定义 world.* 名 → Foundry 服务器静默丢弃，PL emit 的请求 GM 永远收不到。现象极具迷惑性："GM 自己用能成（走本地直调没过 socket），PL 用没反应"。一律用 your-dm-toolkit 那条已开 socket:true 的合法频道，靠 action 字段区分动作。

2. effectmacro 的 onCreate/onDelete 在【effect 拥有者那一端】跑，不是 GM 端。
   把收尾 effect 挂在玩家自己的角色上（如附身的"出窍"），它的 onDelete 就在玩家客户端执行。这时候在 onDelete 里写 if(!game.user.isGM) return; → 整段收尾在玩家端被自己挡掉，啥也没干（GM 端压根没跑这个 effect 的 onDelete）。又是"DM 测正常、PL 翻车"。
   正解：onDelete 不加 GM 守卫，里面需要 GM 权限的活（收回控制权、删敌人标记、代敌人豁免）打包成一个 cleanup，经 socket 委托给 GM 执行。委托函数自己 game.user.isGM ? 直接做 : emit 给 GM。

3. ★最坑★ actor.update({ ownership }) 是【深合并】，不是替换。
   doGrant 往 ownership 里加 PL=3（合并，加成功）。收回时写回"不含该 PL 的旧 ownership 对象" → 合并语义下 Foundry 只是"没动"那个 key，PL=3 纹丝不动地留着，控制权根本没收回。诊断打出来是"恢复后该玩家权限: 3"。
   删一个 ownership key 必须用 Foundry 删除语法：
     await actor.update({ ownership: { ["-=" + userId]: null } });   // 删除该 key
   要还原成旧值就 ownership: { [userId]: 旧值 }。注意 delete localObj[key] 再整体 update 也没用——删的是本地副本，DB 里的 key 照样在。
   （这条对所有"临时给权限再收回"的设计通用：加权限用合并没问题，收权限必须 -= 删除。）

4. unlinked（非链接）token 改谁的 ownership？改【基础世界 actor】的。
   tokenDoc.actor.isToken===true 时，改 tokenDoc.actor（synthetic）的 ownership 不生效；要改 game.actors.get(tokenDoc.actorId) 那个基础 actor，投影 token 继承到 OWNER，玩家才能控制。副作用：附身期间那只怪会临时出现在玩家的角色目录里，收回后消失，正常。

5. 改完 ownership，玩家手里正选着的那个 token 不会自动松手。
   ownership 数据收回 ≠ 玩家当前选中被取消。Foundry 不会去掰开玩家正握着的 token，他还能拖。收回后顺手发个 release 信号（同频道一个 action，所有端都处理、放在 GM 守卫之前），让控制它的客户端 canvas.tokens.get(id)?.release()。再点就因为没权限点不动了。

6. "受伤挣脱"取真实旧 HP 用 preUpdateActor，不靠 updateActor 的 opts。
   preUpdateActor 里 actor.system.attributes.hp.value 还是更新【前】的真血量，拿它和新值比最稳。updateActor 的 opts.dnd5e.hp.value 在 AlwaysHP/midi/手改血 各路径下不可靠，别拿它当门控。另：污染计数器之类"不含 HP 的杂改"会进 updateActor，用"本次 change 里没有 hp.value 就 return"挡掉，避免误触发。

7. 一次性物品自己控销毁，别让系统自动销毁打架。
   附身这种"用了之后还要跑一长串后续"的一次性物品，autoDestroy 设 false、由宏在恰当时机自己删/退费，否则系统中途把物品销毁会打断流程。智力够高免疫这类"没生效"的情况要退费（uses.spent-1）不是销毁。

调这一串的通用方法论：每一步都加一行"诊断 console.log"打出关键值（grant 后权限=?、revoke 后权限=?），用真实数值定位是哪一环没成，别靠猜。这次就是 revoke 诊断打出"还是 3"才一锤定音锁到深合并问题——没有那行诊断，会一直以为是 PL 端没刷新。
