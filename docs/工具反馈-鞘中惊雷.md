# 工具反馈 · 《鞘中惊雷》太刀实战踩坑

> **来源**：另一会话 AI 在做「多活动触发链」武器（太刀《鞘中惊雷》—— 蓄力斩 / 穿刺 line 模板 / 追刃 / 残心）时踩到的 12 条工具反馈，按「带偏程度」排序。
> **本文档记录**：原始反馈 → 我方逐条源码核实（属实 / 不属实 + 证据行号）→ 修复状态 → 验证点。
> **用途**：v1.4.5 发版对着此表验收；以后每次改这几个工具，回来看一眼有没有踩回去。

---

## 总纲（反馈者原话，我认）

> 这套工具写数据没问题，缺的是「**写完之后它到底变成了什么**」的回读层。
> 凡是「我以为对了但实际被清洗」的场景，目前全靠调用方自己写 `execute_js` 探针兜底 ——
> 而 `verified` 又在这个缺口上给了一个**假的安心**。

---

## P0 · 工具主动给了错信号

### 1. `verified:true` 是「操作成功」，不是「值对了」

**现象**：用 `foundry_create_item_minimal` 建完太刀，返回 `verified: true`；但读回发现
`dnd5eactivity100.midiProperties.ignoreTraits` 实际是空 `{}` —— 传进去的 5 个键没落库，工具却报成功。

**复现**：建任意带 `midiProperties` 的物品（活动级或顶层），读回该活动的 `midiProperties`。

**核实结论**：✅ **属实（部分）**
- 证据：`grep "expectFields.push" src/minimal.ts` 得到 27 处，覆盖
  `system.price.value` / `weight.value` / `type.value` / `type.baseItem` / `armor.value` / `strength` /
  `rarity` / `range.units` / `uses.max` / `uses.recovery[0].period` / `capacity.weight.value` /
  `level` / `school` / `identifier` / `classIdentifier` / `activities.*.type` / `activities.*.consumption.targets[0].type`
  / `activities.*.range.units` —— **一处都没有 `midiProperties`**。
- 但 `midiProperties` 的透传有 12 处（`src/minimal.ts` L243 / L885 / L915 / L961 / L1186 等，均 `...mpPatch(...)`），
  **全部无 verify 覆盖**。
- 所以「其余参数都核、只有 midiProperties 不核」—— 反馈者说「唯独没覆盖我传进去的参数」不准确，
  但**它撞上的那个键恰好真在缺口里**，结论正确。

**修复（v1.4.5）**：对每个**显式传入**的 `midiProperties` 键逐条 `expectFields.push`（路径
`system.activities.<活动键>.midiProperties.<键>`），mismatch 即 `verified:false` + 写进 `problems`。

**验证点**：建带 `midiProperties:{ignoreTraits:{idi:["fire"]}}` 的活动 → 故意传一个 dnd5e 不认的键
（如 `ignoreTraits:{bogus:["x"]}`）→ 应报 `verified:false` 并列出该路径。

### 2. `foundry_diff` 报 mismatch 不说原因

**现象**：diff 只回 `{"path":"...","want":[...],"got":null,"reason":"未落库（读回 undefined）"}` ——
**不告诉调用方 dnd5e 侧这个字段的 schema 类型**，所以无法判断是「键名写错了」还是「dnd5e 本来就不接受这个键」。

**复现**：对任意不存在的路径调 `foundry_diff`。

**核实结论**：✅ **属实** —— 返回值确为 `{path, want, got, reason}`，无类型信息
（`src/index.ts` 的 `foundry_diff` handler）。

**修复（v1.4.5）**：`got === undefined` 时进一步探测**父级路径**：
- 父级也 undefined → `reason` 改为「父级路径 X 在该文档上不存在 —— 键名可能写错（dnd5e 的 schema 里没有这一层）」
- 父级存在 → 「父级在，但该字段被 dnd5e 清洗（schema 不接受此键，或类型不符）」
- 另外补充实测值一起回（`gotParent`）。

**验证点**：`expected:{"system.activities.zzz.save.dc.formula":"13"}` → 应报「父级不存在」；
`expected:{"system.nonexistKey":"x"}` → 也报父级不存在；对已知会被清洗的键（如 save 活动的 `includeBase`）
→ 应报「父级在但被清洗」。

## P1 · 逼我多跑一轮，或逼我放弃一个决策

### 3. `activities[].items` 缺 `target` / `template` / `range.value`

**现象**：活动级有 `rangeUnits`，**没有 `rangeValue`**；`target.template`（line / cone / sphere）和
`target.affects` **完全没入口**。而「穿刺」的 line 模板恰恰是这把太刀的核心机制 —— 只能建完再
`foundry_patch_item{activityPatch:...}` 补，或者干脆放弃。

**核实结论**：✅ **属实**
- 证据：`src/minimal.ts:1336-1352` 的 `activities.items.properties` 全表 = `kind / name / activationType /
  damage / save / onSave / check / healing / useFlavor / summon / transform / transformSettings /
  linkedTo / rangeUnits / concentration / midiProperties` —— **无 rangeValue、无 target 任何子键**。
- 另注：主活动那条路（顶层参数）**有** `rangeValue`/`rangeLong`/`rangeUnits`，所以是「额外活动缺」不是「全缺」。

**修复（v1.4.5）**：
- `activities[].rangeValue`（射程数值，写进活动的 `range.value`）
- `activities[].target`（object）：`{template:{type,size,width,height,units,count,contiguous}, affects:{type,count,choice}}`
  —— 结构照 `foundry_reference{topic:"item-fields"}` 的实测形态组装。

**验证点**：建一个带 `target:{template:{type:"line",size:30,width:5,units:"ft"}}` + `rangeValue:30` 的活动 →
读回应有 `target.template.type="line"`、`template.size=30`、`range.value="30"`。

### 4. 静默给所有额外活动加 `consumption:[{itemUses:1}]`，无开关

**现象**：只要物品设了 `uses`，工具就给**每一个**额外活动都配上「消耗 1 次」。「追刃」不该扣残心，被一起配上了。

**核实结论**：✅ **属实，且比反馈者说的更严重**
- 代码里**本来就有开关**：`src/minimal.ts:218`
  `targets: (itemHasUses || s.consumes === true) ? [{ type: 'itemUses', value: '1', ... }] : []`
- **但 schema 从未暴露 `consumes` 这个参数**（`src/minimal.ts:1336-1352` 无此键）
  ⇒ **调用方根本传不进来** —— 从 AI 的视角就是「无开关」，判断正确。

**修复（v1.4.5）**：`activities[].consumes: boolean` 进 schema；并且 `notes` 里显式点名
「已给 N 个活动加 itemUses 消耗（如需个别活动不扣次数，传 `consumes:false`）」。

**验证点**：物品带 `uses.max=3` + 两个额外活动（一个 `consumes:false`）→ 读回：
第一个活动 `consumption.targets[0].type="itemUses"`，第二个 `targets=[]`；`notes` 里出现消耗提示。

### 5. 活动 id 随机，`triggeredActivityId` 天然要两轮

**现象**：主攻击活动 id 是 `pnO86vExH2C3L527` 这种随机串（**追加活动才是可预测的 `dnd5eactivity200`**），
要互相引用就必须「先建 → 读 id → 再 update」，多跑一轮。

**核实结论**：✅ **属实** —— 主活动走「先 create 最小壳 → 再 PUT update」路径，id 由 Foundry `randomID()` 生成，
无法预先知道。

**修复（v1.4.5）**：
- ✅ **预览时列出** `card.activities`（键名一览）+ 新增 `mainActivityNote` 说明「主活动键随机、额外活动键可预测（dnd5eactivity200/300…）」。
- ❌ **「允许指定主活动键名」这条路经实测否决**，已放弃。四组对照实验（世界内实建，各建后即删）：

| 传入 mainActivityId | 落库结果 |
|---|---|
| 不传 | `KE70TAbM5WrBYB2I:attack` —— 干净一个活动 ✓ |
| `strike001`（9 位） | 原键 `GJJ8sLPFjo4qjCXl:attack` **仍在** + 新键被**规范化**成 `2b2dd84360b3189d:?`（type 无效） |
| `dnd5eactivity001` | 原键仍在 + 新键 `dnd5eactivity001:?`（type 无效） |
| `abcdef0123456789`（16 位） | 原键仍在 + 新键 `abcdef0123456789:?`（type 无效） |

  三条硬障碍：① **`-=<旧键>` 在这个更新路径上不生效**（旧活动键始终还在）；
  ② 非 16 位键名会被 dnd5e **规范化**成随机 id；③ 即使键名合法，值是**增量对象**、
  缺 `type` 等必填 ⇒ 落库后活动类型无效。
  ⇒ 结论：**主活动只能沿用 Foundry 生成的随机键**，要引用它请「先建 → `foundry_inspect` 读键 → 再 update」。
  额外活动的键本来就是可预测的，可以直接引用。

**验证点**：预览含 `mainActivityNote`；建完 `activities keys` = `<16位随机>:attack , dnd5eactivity200:save`
（主活动随机、额外活动可预测）；`foundry_inspect{uuid, paths:["system.activities.<随机键>.midiProperties.identifier"]}` 读得到。

### 6. 读不到 `activity.labels`（dnd5e 自算的最终值）

**现象**：「写进去的」和「算出来的」是两回事。`labels.damages` 是唯一能确认伤害对不对的东西 ——
反馈者正是靠它才揪出「追刃算成 2d10」的真 bug。但**没有任何 get 工具返回它**，只能 `execute_js`。

**核实结论**：✅ **属实** —— `labels` 是运行时 `prepareData` 的产物，`GET /get` 返回的是**源数据**，
拿不到派生值。

**修复（v1.4.5）**：`foundry_inspect`（见 #7）加 `labels:true` 选项 —— 走 `POST /execute-js` 读
`item.labels`（含 `activations` / `damages` / `saves` / `toHit` 等），返回精简结构。

**验证点**：对一把 1d8+3 的武器调 `foundry_inspect{uuid, labels:true}` →
`labels.damages` 里出现含 `1d8` 与 `+3` 的条目。

---

### 7. 没有「一次读回指定字段」的入口

**现象**：`summary:true` 把活动细节精简掉了；要看某个活动的精确字段，只能 `execute_js` 手写路径逐个取。

**核实结论**：✅ **属实** —— 只有 `foundry_diff`（必须给 `expected`，是「比对」不是「读取」），
没有 `foundry_inspect{uuid, paths[]}`。

**修复（v1.4.5）**：**新增第 95 个工具 `foundry_inspect`**：
```
foundry_inspect{uuid, paths?: string[], labels?: boolean}
→ { uuid, name, type, values:{<path>:<值>}, missing:[<不存在的路径>], labels?:{...}, hint }
```
路径语法同 `foundry_diff`（点号 + `[n]` 下标）。

**验证点**：`foundry_inspect{uuid, paths:["system.damage.base.denomination","system.activities"]}` →
返回两个值；不存在路径进 `missing` 而不是静默消失。

## P2 · 静默失败风险与摩擦

### 8. `search_animation` 返回 dbPath 却不标 entryExists

**现象**：列表里返回 `jb2a.melee_attack.04.katana.01`，实际要写成 `.0` 才能播；
而 AA 的路径**填错是静默不播、无报错**。

**核实结论**：✅ **属实** —— `foundry_search_animation` 只回 `{dbPath, file, module}`；
`Sequencer.Database.searchFor` 给的**未必是叶子路径**（可能是前缀节点）。

**修复（v1.4.5）**：对返回的 **top-N 条**（默认全部返回项，上限 `limit`）调
`Sequencer.Database.getEntry(path)` 验证，命中者标 `verified:true`，未命中者标 `verified:false`
并在 `hint` 里提示「该路径是前缀节点，用 `entries` 里的完整路径」。

**验证点**：搜 `katana` → 返回项应带 `verified` 字段；对故意拼错的路径应标 false。

---

### 9. 搜 `thrust` 回 0 条，不给替代词

**现象**：只提示「换个更粗的词根」，**不告诉换哪个** —— 反馈者试到 `spear` 才出结果。

**核实结论**：✅ **属实**。

**修复（v1.4.5）**：内置同义词表，0 结果时**自动重搜**并回报用了哪个词：
```
thrust → stab / pierce / spear / lunge / jab / rapier
punch  → fist / unarmed / knuckle
```
（表放 `src/tools-extra.ts`，只在 0 结果时触发，不改变原有命中行为。）

**验证点**：搜 `thrust` → 返回体里应带 `usedSynonym:"spear"`（或首个命中的词）而非空结果。

---

### 10. flags 的合并语义没说明

**现象**：深合并还是覆盖？不确定就只能按最坏情况**全量重写**（AA 九个顶层键 + sound 七字段）。

**核实结论**：⚠️ **待核实** —— 已知 `foundry_patch_item` 的 `flags` 参数走深合并，
但工具描述里确实没写清。

**修复（v1.4.5）**：在 `foundry_patch_item` / `create_item_minimal` / `update_entity` 三处描述里
写明「**flags 是深合并**（只覆盖你给的那几个叶子键，同层的其它键保持原值）；
`unsetFlags` 走点号路径删除」。

**验证点**：对已有 AA flags 的物品 patch `{autoanimations:{sound:{volume:0.5}}}` →
读回应保留原 `primary.video.*`，只有 volume 变。

---

### 11. `create_entity{Macro}` 被拦时报了设置名，没给设置 id

**现象**：报错说需要开「Allow Macro Creation/Editing」，但**设置 id `foundry-rest-api.allowMacroWrite`**
要另外扫 `game.settings` 全表才拿到。

**核实结论**：✅ **属实** —— 这是**模块端**（foundry-rest-api）的报错文案，我们改不了它的输出，
只能在工具描述里补对照表。

**修复（v1.4.5）**：`create_entity` / `macro_execute` 描述里补一行：
「⚠️ 报错提到 Allow Macro Creation/Editing 时，去 **Foundry 设置 → 模块设置 → Foundry REST API**
把对应的开关打开（设置键 `foundry-rest-api.allowMacroWrite`）」。

**验证点**：描述里能搜到 `foundry-rest-api.allowMacroWrite`。

---

### 12. schema 无枚举的字段，没有惯例值可参考

**现象**：`triggeredActivityTargets` 探针显示无 choices，参考库也没写它实际怎么用 ⇒ 放弃了这个决策点。

**核实结论**：⚠️ **部分属实** —— `foundry_reference{topic:"midi-properties"}` 里**有** 7 种 targets
场景表（`self` / `hitTargets` / `missedTargets` / `failedSaves` / `saveTargets` / `targets` / `retarget`），
**但工具 schema 的描述里没接上**，AI 不知道要去翻。

**修复（v1.4.5）**：把 targets 七值与各自语义**直接写进 `activities[].midiProperties` 的 schema 描述**，
并注明「完整 29 键见 `foundry_reference{topic:"midi-properties"}`」。

**验证点**：`foundry_create_item_minimal` 的 parameters 里，`midiProperties` 描述含 `hitTargets` 与 `failedSaves`。

## 一句话留给下一个改这些工具的人

反馈者最后那句值得贴在墙上：

> 修好前 12 条里最前面的那几条，**比再添十个新工具都值**。

因为工具失败的模式高度一致 —— **不是报错，是「成功」**：
回执说 success，数据却是错的或缺的。调用方于是条件反射地对每次写入都读回，
调用数直接翻倍。让「成功」不再骗人，比多给十个能力都管用。
